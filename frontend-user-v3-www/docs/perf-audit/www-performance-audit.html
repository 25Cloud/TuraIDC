图拉云官网 www 前端（Vue 3.5 + Vite 6 + Element Plus 2.9）整体架构健康：路由全懒加载、manualChunks 划分合理、Element Plus 样式按组件拆分、构建期预压缩 .gz/.br、preconnect / fetchpriority 均已就位。但首页 LCP 关键路径存在「JS 链 → 两跳动态 chunk → 跨域 API」三级串行且 API 无预热、入口渲染阻塞 CSS 含约 17KB 默认主题死字节、branding SVG（74KB / 43KB）超规格且作为 favicon 每页必载——这三大瓶颈直接拖住首屏指标。

B良

整体健康度评级 B（良）。建议优先处理：API 预热 + 路由链 modulepreload（P0-1）、入口 CSS 去默认主题死块并异步化（P0-4）、SVG 重生成（P0-5）。配合 en locale 与 seo 数据瘦身、popper 换轻量实现，可将首页首屏 JS 从约 138KB br 降至约 110KB br，LCP 从约 2.5–4s 压到约 1.8–2.5s。

三大核心瓶颈

按对首屏 / Core Web Vitals 的影响排序，建议作为第一轮修复。

BOTTLENECK 01

首页 LCP 被 /v2/site/home API 串行阻塞，且关键路由 chunk 无预热

LCP 元素要等 JS 关键链执行完、onMounted 才发 API、返回后才 v-if 渲染；入口只 preconnect+prefetch config，对 home 接口与首页 chunk 均无预热。形成「entry → 布局+popper → 首页 → API」四级串行，API 往返约 150–400ms 属可避免。

BOTTLENECK 02

入口渲染阻塞 CSS：约 17KB 默认主题死字节 + 28KB 阻塞 FCP

bootstrap 手工引入 message 预编译 CSS 把 EP 默认主题 base.css（含未覆盖的 --el-color-primary-rgb）打进入口 CSS，阻塞 splash 首绘约 75–150ms，弹层主题还依赖脆弱的 CSS 顺序。

BOTTLENECK 03

branding SVG 严重超规格：74KB / 43KB，favicon 每页必载

logo1.svg（favicon+splash）与 logo.svg（页头/页脚）是单个极复杂 path 的自动描边，压缩后仍 48KB br，与 entry JS 争抢首屏关键带宽。

直接影响 LCP / FCP / 首屏体积，建议第一轮修复。

P3 · 低优先级

  • P3-1 dayjs 冗余：package.json 声明但全项目无直接使用，作为 EP 内部传递依赖经 WebsiteLayout 静态引用进入每页首屏（base chunk 7KB raw / 2.8KB br）。修复：确认布局链哪个 EP 组件传递引入；从 dependencies 移除；或对 dayjs 做 sideEffects 标记避免进布局链。（package.json / WebsiteLayout.vue）
  • P3-2 页头/页脚 logo <img> 缺 width/height：CSS 已固定尺寸无 CLS，仅规范缺口。修复：补 width="148" height="32"/"40" 显式声明。（WebsiteLayout.vue 7-13/456-462）
  • P3-3 死资源：public/img/os/ 下 cart.svg、slider.svg、no-upgrade.svg 全仓库无引用。修复：确认后删除或归档。（public/img/os/）
  • P3-4 axios GET 去重 key 不含 Authorization：buildSafeRequestKey 仅取 method/baseURL/url/params/data，同 URL 同 params 的 GET 若一个在 token 就绪前、一个在就绪后并发会共享先发起者的（可能未鉴权）响应。修复：key 增加 header 维度或对带 token 的 GET 关闭去重。（@turaidc/shared/runtime/http/core.ts 39-49）
  • P3-5 catalogPendingMap 取消后静默空载：切组 abort 后 pending map 中未 settle 的已取消 promise 被再次命中，await 抛 CanceledError 被 catch 静默吞掉且不重试，组 A→B→A 连点时组 A 可能停在空态无自愈。修复：pending 命中时先判断是否已因取消而拒绝，catch 到 CanceledError 且 token 仍匹配时重新发起。（useWebsiteProductsCatalog.js 380-394/413-418）

验证建议

  1. 体积验证：每项修复后执行 npm run build，比对 dist/assets 与 dist/index.html——入口 CSS 是否仍含默认主题块（--el-color-primary-rgb:64,158,255，应为 0 处）；入口 JS 是否仍含 name:"en" 与 5 个落地页 slug；用 du -b dist/assets/js/*.js 比对对应 chunk 体积变化。
  2. 行为验证：fetchAll 终止保护——mock 接口返回 total 恒定且第 N 页空 list，确认循环在空页/上限处退出；深链目录去重——进 /products?typeId..&groupId.. 观察 Network，确认 purchase-context 之后不再重复拉 product-groups + 目标组目录；详情预取中止——选中商品后确认剩余详情请求出现 canceled。
  3. 指标验证：Lighthouse / PageSpeed Insights（4G + Moto G）对比改动前后——LCP 候选元素类型从 video 变为 h1/poster 且数值变化；FCP 确认 splash 首绘不再等 28KB 入口 CSS；CLS 观察 hero 骨架替换瞬间是否还有 30–80px 位移；用 PerformanceObserver 确认 LCP 元素与绘制时间戳。
  4. 主题正确性：修复 bootstrap sass 路径后，确认 ElMessage 弹层颜色仍为主题蓝 #165dff（而非默认 #409eff），且 global.scss 补齐 primary-rgb 后 rgba(var(--el-color-primary-rgb),…) 渲染正确。
  5. 真机弱网：DevTools Network 节流（Slow 4G）抓首页首屏请求瀑布，期望 modulepreload 与 /v2/site/home 并行，不再出现四级串行。
审查方法：6 个维度专家（打包与首屏 / 图片与媒体 / 运行时渲染 / 网络与 API / 框架使用 / Core Web Vitals）并行审查源码与构建产物，再由综合评审专家去重合并、按 P0–P3 排序。所有发现均带可核查证据（文件 + 行号）。指标估值为 4G / 中端机下的保守估算，实际以 Lighthouse 实测为准。
