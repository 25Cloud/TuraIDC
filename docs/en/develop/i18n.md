# Internationalization (i18n) Standard

The three TuraIDC frontends (`frontend-admin-v3` / `frontend-user-v3-www` / `frontend-user-v4-console`) and the backend
support **four languages** in a unified way: Simplified Chinese, Traditional Chinese (Taiwan), Traditional Chinese (Hong Kong), English.

The frontend owns UI copy, the backend owns validation messages and business exception messages, and both sides share one set of locale codes. This document is the single source of truth; changing a language, adding copy, and wiring up a UI that is not yet internationalized all follow it.

See `backend/tests/Unit/I18nLocaleConsistencyTest.php` for the automated test; it blocks the vast majority of regressions before a build.

---

## 1. Language set

| Code    | Language                        | Description                                                            |
| ------- | ------------------------------- | ---------------------------------------------------------------------- |
| `zh_CN` | Simplified Chinese              | **Source of truth for entries**. All copy is written here first        |
| `zh_TW` | Traditional Chinese (Taiwan)    | Generated from `zh_CN` via OpenCC `cn→twp`, **not maintained by hand** |
| `zh_HK` | Traditional Chinese (Hong Kong) | Generated from `zh_CN` via OpenCC `cn→hkp`, **not maintained by hand** |
| `en_US` | English                         | Human translation                                                      |

### Traditional Chinese must be split into Taiwan and Hong Kong

Traditional Chinese characters are mostly identical; the difference is in the vocabulary chosen, and the two are not interchangeable:

| 简体 | 台灣 `zh_TW` | 香港 `zh_HK` |
| ---- | ------------ | ------------ |
| 数据 | 資料         | 數據         |
| 网络 | 網路         | 網絡         |
| 软件 | 軟體         | 軟件         |
| 用户 | 使用者       | 用戶         |
| 文件 | 檔案         | 文件         |
| 默认 | 預設         | 默認         |
| 视频 | 影片         | 視頻         |
| 邮箱 | 電子郵件     | 電郵         |

Covering both regions with a single set of Traditional Chinese entries leaves half the terminology wrong.

The codes follow the native naming of TDesign / Element Plus; variants such as `zh-Hans` are not invented, so the component library language packs mount directly.

**The default language is `zh_CN`**, and `fallbackLocale` is `zh_CN` as well: when any language is missing an entry it falls back to Simplified Chinese instead of showing a blank or a bare key.

### Where the locale comes from

```
localStorage 里的 turaidc-locale / tdesign-starter-locale
  → 命中 supportedLocales 则采用
  → 否则 zh_CN
```

The admin panel and the user console use `tdesign-starter-locale` from the TDesign starter; the official website uses its own `turaidc-locale`. The two do not interfere with each other because they are separate applications.

## 2. Entry files and key naming

```
frontend-<app>/src/locales/
├── index.ts          # createI18n、supportedLocales、组件库语言映射
├── useLocale.ts      # changeLocale / locale / getComponentsLocale
└── lang/
    ├── zh_CN.json    # 真源
    ├── zh_TW.json    # 生成
    └── en_US.json    # 人工翻译
```

The three files are nested by dotted path, and **the key sets must be exactly identical** (the test verifies this).

Key naming: lower camel case, dot-separated, **starting with the feature module**, with the module name inferred from the file path:

| Module               | Example                                                  |
| -------------------- | -------------------------------------------------------- |
| `layout`             | `layout.header.aboutUs`, `layout.nav.productCatalog`     |
| `product`            | `product.detail.basePrice`, `product.specSelection`      |
| `content`            | `content.notice.empty`, `content.help.searchPlaceholder` |
| `seo` / `seoLanding` | `seoLanding.usServer.hero.title`                         |
| `common`             | `common.osPicker.version`                                |

Rules:

- Starts with a lowercase letter, camelCase; no Chinese characters, no spaces
- One meaning, one name site-wide (`viewAllProducts` must not also be written as `seeAll`)
- Name by semantics, not by position (`product.detail.totalFee` beats `product.detail.label3`)

## 3. Translation boundaries (the section where things break most often)

### Must be translated

- Template text nodes: `<div>暂无数据</div>`
- Copy attributes: `title` / `placeholder` / `alt` / `aria-label` / `label` / `description` /
  `content` / `empty-text` / `confirm` / `cancel`
- Strings in scripts that are **purely for human display**: `MessagePlugin.error('保存失败')`, `label: '状态'`

### Must never be translated

| Type                                    | Real example                                  | Reason                                                                                                                                              |
| --------------------------------------- | --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Keyword constants used for matching** | `CPU_KEYWORDS = ['cpu','core','处理器','核']` | Used for string matching against the `field`/`name` of product config options. Translating them kills every match and product spec detection breaks |
| Protocol fields / API parameters        | `configoption`, `zapfxxg`, `regdate`          | The peer parses them literally                                                                                                                      |
| Status literals                         | `'pending'`, `'active'`                       | Coupled to the backend enums                                                                                                                        |
| Brand names / domains                   | `TuraIDC`, `25y.cn`                           |                                                                                                                                                     |
| Code identifiers                        | Variable names, route paths, component names  |                                                                                                                                                     |
| Placeholders                            | `{count}`, `{size}`, `%s`                     | The structure cannot change                                                                                                                         |

> **This one is a hard-won lesson.** A script once replaced `处理器` and `核` inside `CPU_KEYWORDS` with `$t()`,
> and the CPU/memory classification on the official website stopped working. **Any string you cannot confirm by eye as human-facing is left alone.**

### How to decide

Ask yourself one question: **does system behavior change once this string is modified?**

- It changes (matching, protocol, enums) → do not translate
- It does not change (display only) → translate

## 4. Wiring it in

### Use `$t()` in templates

`createI18n({ globalInjection: true })` is enabled, so templates can use it directly, **no import needed**:

```vue
<h1>{{ $t('product.list.breadcrumbRoot') }}</h1>
<input :placeholder="$t('product.detail.systemPlaceholder')" />
```

### Use `t()` in scripts

```js
import { t } from "@/locales";
MessagePlugin.error(t("common.saveFailed"));
```

### When a text node mixes content

Replace only the matched fragment and keep the surrounding text:

```vue
<!-- 原文：产品中心 · 选择一级分组 -->
<h1>{{ $t('product.list.breadcrumbRoot') }}</h1>

<!-- 原文：共 {{ n }} 条数据 -->
<p>共 {{ $t('common.total') }} {{ n }} {{ $t('common.records') }}</p>
```

### Component library language linkage

- **TDesign** (admin / console): `tdesignLocaleMap` is attached to the entries' `componentsLocale`, and
  `getComponentsLocale()` takes it out and passes it to `useLocale()`.
- **Element Plus** (official website): carried by `<el-config-provider :locale="elementLocale">` in `App.vue`,
  with that value supplied by `getComponentsLocale` from `useLocale()`. **Do not** pass the locale through
  `provideGlobalConfig` any more; its types do not accept `Ref` and it is not reactive at runtime.

## 5. Workflow for adding copy

1. Write the `zh_CN` copy **in the component**
2. Add the matching `en_US` entries in the same pass (keys aligned with `zh_CN`)
3. `zh_TW` is not hand-written; run the generation script
4. Run the tests

```bash
# 重新生成三端的 zh_TW（zh_CN 改动后执行）
node backend/scripts/i18n/build-zh-trad.mjs

# 护栏测试
cd backend && php artisan test --filter=I18nLocaleConsistency
```

### Traditional Chinese conversion (Taiwan / Hong Kong)

Use **OpenCC** throughout; do not hand-write a simplified-to-traditional mapping table — hand-written tables
do not cover everything, and in testing 447 characters were missed, producing mixed output such as 「關於我们」.

```js
import OpenCC from "opencc-js";
const twp = OpenCC.Converter({ from: "cn", to: "twp" }); // 台湾
const hkp = OpenCC.Converter({ from: "cn", to: "hkp" }); // 香港
```

Terms that neither converter covers are added in `backend/scripts/i18n/build-zh-trad.mjs`, and
**the replacement timing must be distinguished**:

- `HK_PRE_TERMS` — replaced **before** opencc. Applies to terms such as 「内存→記憶體」 where opencc performs
  no vocabulary mapping (`hkp` leaves 「内存」 as 「內存」).
- `HK_POST_TERMS` — replaced **after** opencc. The Hong Kong dictionary restores some characters to simplified
  forms (`户`, `税`, `温`), so they must be changed back after conversion; otherwise the output is not Traditional Chinese at all.

## 6. Test guardrails

`backend/tests/Unit/I18nLocaleConsistencyTest.php` verifies:

1. The key sets of the four entry files are exactly identical
2. `zh_TW` / `zh_HK` contain no leftover simplified characters
3. Each app's `supportedLocales` matches the entry files that actually exist and covers all four languages
4. The component library language mapping covers every locale (miss one and pagination/date component copy stops following the switch)
5. Keys referenced by `$t('key')` / `t('key')` in code must exist in the entries, otherwise the UI shows the bare key
6. No hard-coded Chinese is left in the template layer

> TDesign has no standalone Hong Kong language pack (only `zh_TW`), so the component language for
> `zh_HK` maps to `zh_TW`; Element Plus ships `zh-hk` and it is mounted directly.

**If you add copy without the `en_US` entries, or forget to re-run the generation script for `zh_TW`/`zh_HK`, the test fails outright.**

## 7. Backend business messages

### 7.1 Language negotiation

The `SetLocale` middleware (registered at the front of the api stack) decides the current locale, in this order:

1. `X-Locale` request header — the current language of the frontend i18n, attached by the axios interceptor of all three apps, the most accurate;
2. `Accept-Language` — browser language preference (recognizes `zh-HK` / `zh-TW` / `en-GB` etc., including q-value ordering);
3. `zh_CN` by default.

After switching language in the frontend, no refresh is needed; it takes effect immediately.

### 7.2 The message table uses the Chinese source text as the key

In `backend/lang/{locale}/messages.php` the key is exactly the Chinese source text written when the exception is thrown:

```php
// zh_TW/messages.php
'商品分组不存在' => '商品分組不存在',
// en_US/messages.php
'商品分组不存在' => 'The product group does not exist',
```

This has three benefits:

- **Zero changes at call sites** — not one of the 600-plus `throw new BusinessException('中文')` lines needs touching;
  translation happens only when `BusinessException` is constructed;
- **Natural fallback** — a new business message without a translation misses the lookup table and returns the Chinese source text, never an empty message;
- **Incremental** — no need to maintain a complete word list for every language at the same time.

> A lookup **must carry the group prefix**: `Lang::get('messages.' . $message)`.
> Laravel treats a key without a dot as a group name (it looks up `消息文本`[null]) and it never matches.

### 7.3 Generation script

```bash
node backend/scripts/i18n/build-biz-messages.mjs
```

Scans every `BusinessException('...')` in `backend/app` and regenerates `zh_CN` / `zh_TW` / `zh_HK`.
`en_US` is the product of human translation and the script does not overwrite it — missing translations are reported by the test.

### 7.4 Logs are not affected by language

Each call layer logs the **Chinese source text from before the exception was thrown**, so troubleshooting is not affected by the UI language.

## 8. Where the switcher goes

| App                | Location                               | Reason                                                                                          |
| ------------------ | -------------------------------------- | ----------------------------------------------------------------------------------------------- |
| admin / v4-console | Settings panel (`layouts/setting.vue`) | TDesign starter convention, next to theme and layout settings                                   |
| Official website   | Footer (`WebsiteLayout.vue`)           | The official website has no settings panel; the footer does not interfere with the first screen |

Language names are displayed in each language's own script (`简体中文` / `繁體中文` / `English`) and are **not translated** —
they come from the top-level `lang` field of each entry file.

## 9. The docs site uses the same language set

The `docs/` site is no longer monolingual: Simplified Chinese occupies the root path, and `/en/`, `/zh-tw/`, and `/zh-hk/` are each a mirrored subtree. The language codes match the four apps above, and URL prefixes use the short form (`zh-tw` rather than `zh_TW`).

Two differences are worth remembering:

- **Chinese is the only source of truth.** English is a human/AI translation, and a page's front matter records `source` and `sourceHash`, so it may lag behind after a Chinese change; the two Traditional Chinese trees are generated straight from Chinese by OpenCC, so any Chinese edit must be followed by re-running the generation script, or the docs check fails.
- **Translations never touch code blocks.** Code, commands, and config keys are kept verbatim in translations, and the check script compares code blocks, heading levels, and link targets — translating any one of them raises an error.

The exact commands, the front matter contract, and the glossary live under `docs/internal/i18n/` in the repository and are not repeated here.
