# API Documentation

TuraIDC maintains its interface contracts in three layers, with no overlapping responsibilities: start with the format specification, use the catalog navigation to locate the business domain, and finally look up the specific route in the auto-generated catalog.

## 1. Three Entry Points

| Document                                                | Question It Answers                                                                             | Maintenance                                   |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | --------------------------------------------- |
| [Interface Format Specification](format.md)             | What the response structure, authentication, pagination, validation, and version boundaries are | Maintained by hand                            |
| [API Catalog Navigation](catalog-navigation.md)         | What capabilities a business domain has, and which endpoints the core business flows map to     | Maintained by hand                            |
| [Backend API Catalog](/develop/api/backend-api-catalog) | The complete enumeration of routes, methods, and controller actions                             | Generated by script; manual editing forbidden |

The catalog navigation and the format specification both defer to the regenerated catalog; when the three conflict, fall back to the code and tests in that order.

## 2. Refresh the Auto-Generated Catalog

Re-run it whenever routes or controller actions change; the artifact is out of scope for manual maintenance:

```bash
php backend/scripts/export_api_inventory.php
```

After refreshing, run the documentation check to confirm the table of contents and links are still complete:

```bash
pnpm run docs:check
```

## 3. Interface Layering Conventions

- Admin endpoints all live under `/api/v2/admin/*`, client endpoints under `/api/v2/client/*`, and site public data under `/api/v2/site/*`.
- The open API (the key-authenticated interface called by external systems) and the ZJMF upstream protocol are separate entry points; see [ZJMF Upstream Protocol](../integrations/zjmf-upstream-api.md) and [Backend Guidelines](../backend.md).
- Keep controllers thin: validation goes into FormRequest, business logic into a Service, and third-party calls into a Driver or plugin.
- Privilege escalation and authentication issues must be resolved at the authentication and authorization layer, and must not be backstopped by the WAF.
