# 自助退款

插件目录为 `backend/plugins/addons/auto_refund/`，后台能力域为 `addons`，标识为 `auto_refund`。它把「用户想退掉某台机器」从工单搬到控制台：用户自己选机器、填原因、提交；插件按**该商品**配置的退款策略算出可退性并分流到对应通道，最后在台账里留痕，由管理员核对上游后结算到用户余额。

行为口径对齐智简魔方财务的 AutoRefund 插件（v1.3.0）：四种退款类型、三种退款规则、三种退款要求，全部**按商品**配置。真实退多少钱仍以上游与实际结算为准，本站展示的金额是预估。

## 1. 四个概念

| 概念     | 取值                                            | 说明                                                                   |
| -------- | ----------------------------------------------- | ---------------------------------------------------------------------- |
| 退款类型 | 人工审核 / 自动退款 / API 工单退款 / 插件间对接 | 决定提交后走哪条路：只落台账、立即退款、向上游开工单、调上游 `api.php` |
| 退款规则 | 按时长 / 按月 / 全额                            | 决定预估金额怎么算（公式见第 6 节）                                    |
| 退款要求 | 产品首次 / 同类产品首次 / 指定时间内            | 决定「谁还能申请」：同商品首次、同一级商品分组首次、开通后 N 小时内    |
| 时间窗口 | 小时                                            | 只有「指定时间内」这一要求会用到，`0` 表示不限                         |

同一商品同时只能有一种类型、一种规则、一种要求——这与上游一致，不要指望「既按时长又按月」。

## 2. 安装与启用

1. 部署后端并跑一次 `php artisan migrate`。建表与登记都由**核心迁移**完成（插件不能自注册迁移）：
   - `2026_11_01_000001_create_auto_refund_applications_table`：申请台账；
   - `2026_11_01_000002_register_auto_refund_plugin`：登记插件，**只登记、默认不启用**；
   - `2026_11_03_000001_create_auto_refund_product_rules_table`：商品退款策略；
   - `2026_11_03_000002_add_channel_and_ticket_to_auto_refund_applications`：台账补通道与工单字段。
2. 管理端「插件管理」→ 自助退款 → 填配置（第 3 节）→ 启用。
3. 管理端「财务管理 → 自助退款 → 退款商品策略」给商品逐条配策略（第 4 节）。**没配策略的商品不会出现在用户的可申请列表里**。
4. 重新构建并部署两个前端（`frontend-user-v4-console`、`frontend-admin-v3`）。

插件停用后两端入口自动收起（`OptionalFeature::map()` 的 `auto_refund`），接口随之消失；已产生的台账与策略保留。

## 3. 配置项

**上游接口通道（退款类型 = 插件间对接时才必须）**

| 配置               | 默认                    | 说明                                                                   |
| ------------------ | ----------------------- | ---------------------------------------------------------------------- |
| 启用自助退款       | 开                      | 关闭后控制台显示未开放                                                 |
| 上游接口地址       | 上游 `api.php` 完整地址 | 必须是 POST 端点；只在「插件间对接」类型下使用，留空则该通道判定未就绪 |
| 上游 API KEY       | 空                      | 上游发放的完整密钥；页面上的掩码值无效；加密保存、不回显               |
| 请求超时（秒）     | 15                      | 超时按「结果未知」处理并占住该机器的提交闸门                           |
| 提交前校验上游主机 | 开                      | 提交前先 `query` 确认机器在上游可见                                    |
| 控制台说明文案     | 空                      | 展示在退款中心顶部                                                     |
| 结算备注模板       | 自助退款申请结算        | 写进退款单的备注前缀，后端会附申请编号                                 |

**上游工单通道（退款类型 = API 工单退款时才必须）**

| 配置            | 默认               | 说明                                                                                                                             |
| --------------- | ------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| 上游工单协议    | `zjfm`             | `zjfm`：智简魔方财务原生（`/v1/login_api` 换 JWT → `/submitticket`）；`tura`：上游也是 TuraIDC，走既有 `/ticket/create` 投递链路 |
| 上游站点地址    | 空                 | `zjfm` 协议必填                                                                                                                  |
| 上游账号        | 空                 | `zjfm` 协议的登录账号                                                                                                            |
| 上游 API KEY    | 空                 | `zjfm` 协议登录用的密钥，加密保存                                                                                                |
| 上游工单部门 ID | 2                  | 上游「财务/退款」部门的 `dptid`，填错就是把工单发错部门                                                                          |
| 工单标题模板    | 申请退款           | 支持 `{product_name}` `{host_id}` `{amount}` `{reason}`                                                                          |
| 工单内容模板    | 申请产品无理由退款 | 同上                                                                                                                             |

`zjfm` 协议的成功判据是上游返回 **302 且 Location 含 `supporttickets`**（上游原生接口就是这个行为），也兼容返回 JSON `code=200` 的变体；两种都不满足时会在台账里留下失败原因与响应前 300 字。

## 4. 给商品配策略

管理端「财务管理 → 自助退款 → 退款商品策略」：

- 列表能看到**所有商品**，包括还没配的（状态显示「未配置」）。筛选可按关键字与配置状态。
- 逐条编辑：退款类型、退款规则、退款要求、时间窗口（小时）、启用开关。
- `window_hours` 只有选中「指定时间内」才可填；填 `0` 等同不限。
- 关掉启用开关 = 该商品不参与自助退款，用户侧看不到。

选择建议：

| 场景                                     | 类型         | 说明                                                   |
| ---------------------------------------- | ------------ | ------------------------------------------------------ |
| 想让客服逐单看                           | 人工审核     | 只落台账，不外发任何请求                               |
| 小额、规则简单、信任公式                 | 自动退款     | 提交即退款到余额，无需人工                             |
| 上游是智简魔方财务，要留沟通记录         | API 工单退款 | 建本站工单 + 向上游提工单，上游回复进工单线程          |
| 上游已装 AutoRefund 并对本站发了 API KEY | 插件间对接   | 直接调 `api.php` 的 `submit`，用户可在待审核时自己取消 |

## 5. 用户与管理端流程

用户侧（控制台「交易记录 → 退款中心」）：

1. 候选列表只列**本站已开通、且该商品配了策略**的机器；每行标注该机器自己的「类型 · 规则 · 要求」，例如「插件间对接 · 按时长折算 · 产品首次」。
2. 不可申请的行会写明原因（该商品未开放、未支付、已过期、已续费、升降级过、免费订单、状态不支持、已有在途申请、超出时间窗口、上游不可用等）。
3. 提交后按类型给不同话术：自动退款＝已退款到余额；人工审核＝等待管理员审核；API 工单＝已向上游提交工单；插件间对接＝已提交上游审核。
4. 只有「插件间对接 + 待上游审核」的申请能自己取消；其它类型没有可撤销的上游记录，页面不会给取消按钮。

管理端（「财务管理 → 自助退款 → 退款申请」）：

| 操作         | 作用                           | 注意                                                                     |
| ------------ | ------------------------------ | ------------------------------------------------------------------------ |
| 结算         | 按填写金额退款到用户余额       | 走既有退款链路，超出账单剩余可退额会被账务层拒掉；先到上游核对是否已到账 |
| 驳回         | 标记驳回，不入账               | 上游拒绝后在这里收口                                                     |
| 作废         | 强制关闭卡死/结果未知的申请    | 唯一手动出口，不可撤回，不退款                                           |
| 测试上游连接 | 调 `query` 回报机器数与时间差  | 排查密钥、地址、出网、时钟偏差                                           |
| 上游机器对账 | 列出上游全部机器与本地绑定情况 | 找「上游有本地没绑」与「本地绑了上游没了」                               |

详情抽屉里能看到退款类型、通道、本站工单、上游工单号与**提交时的策略快照**——策略是可改的配置，没有快照就没人能解释「当时为什么这台能退、金额怎么算的」。

## 6. 金额与校验口径

预估金额按上游公式：

```text
周期秒数 = 到期时间 - 开通时间
每秒单价 = 首购账单实付 / 周期秒数

按时长：实付 - 每秒单价 * 已用秒数
按月：  实付 - 每秒单价 * 2592000 * ceil(已用秒数 / 2592000)
全额：  实付
结果四舍五入到分；小于等于 0 直接拒绝申请。
```

- 机器处于「未开通完成」状态时强制按全额算，不看商品配置的规则。
- 三个基数取自本站：**开通时间 = 服务创建时间**、**到期时间 = 服务到期时间**、**首购实付 = 开通那一单的账单实付额**（不是最近一次续费账单）。
- 预估只用于展示与工单模板占位；插件间对接通道**不把金额传给上游**（上游契约不允许指定金额），实退以管理员结算为准，且受既有可退上限保护。

提交前的硬性校验（任一命中即拒绝）：商品没配策略、首购账单未支付、已有在途申请、已过期、服务已删除、服务状态不支持、已续费、首付为 0、升降级过。

## 7. 排错

| 现象                             | 排查                                                                                  |
| -------------------------------- | ------------------------------------------------------------------------------------- |
| 用户看不到某台机器               | 该商品有没有配策略并启用；机器是否绑定了上游实例（工单/接口通道需要）                 |
| 提交提示「该商品未开放自助退款」 | 策略行缺失或 `enabled=0`                                                              |
| 提交提示「未配置上游工单部门」   | `zjfm` 协议的部门 ID 为空；`tura` 协议既没配部门也没有匹配的工单投递规则              |
| 工单通道报 302 但判定失败        | Location 不含 `supporttickets`，通常是账号无工单权限或部门 ID 不存在                  |
| 插件间对接报 401 / 403           | API KEY 无效 / 上游插件授权过期                                                       |
| 申请卡在「结果未知」             | 上游超时或返回非 JSON。先到上游核实是否已建单，再结算或作废；期间用户重提会被闸门挡住 |
| 结算报「超过原单可退金额」       | 账单剩余可退额不足，按可退额调整                                                      |
| 用户说上游退了但余额没变         | 上游退款 ≠ 本站结算：台账里点「结算」才会入用户余额                                   |
