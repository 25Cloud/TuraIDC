# CLA 可行性核对（双许可模式）

## 结论

在完成文末「剩余法务确认」的前提下，`CLA.md` v1.0（2026-10-21 生效）可以作为 TuraIDC AGPL-3.0-or-later + 商业许可双许可模式的贡献授权基础。

- **授权链条成立**：CLA 采用「版权许可 + 专利许可 + 明确再许可（sublicense）」，不是版权转让；项目方可以同时按 AGPL 与商业许可分发同一份贡献。
- **贡献者权利保留**：贡献者仍是版权人，署名保留；已按 AGPL 获得的公众权利不因 CLA 减少。
- **历史贡献可处理**：生效日前贡献默认不追溯，贡献者可自愿补签覆盖；未补签的第三方代码不进入商业版本，商业交付前按清单核对。
- **仍需法务确认**：签约主体、适用法律与争议解决、精神权利可执行性、职务作品授权、电子签署证据形式与保存期限。

> 本文是工程侧核对记录，不构成法律意见；正式商用前必须由法务或专业律师复核 `CLA.md` 与 `LICENSE-COMMERCIAL.md`。
>
> **2026-10-21 法务审查后的修订**：审查确认本文当时的「历史贡献有解」结论需要收紧——文件级排除在 AGPL 第 0/5(c) 条下不成立，能切断授权链的只有补签（R1）或分离构建 + 独立实现（R2）；且仓库约七成文件来自一次性导入提交，权属需另行举证。据此，`CLA.md` 已新增「商业版本构建规则」章节，本文结论以该章节与[签署记录与覆盖清单](cla-signing-register.md)为准。

## 生效与历史贡献口径

- **生效日期**：2026-10-21。
- **生效日后**：新贡献必须签署 CLA 才能合并，自动纳入 AGPL + 商业双许可。
- **生效日前**：
  - 默认按原 AGPL 授权，不自动适用 CLA；
  - 项目方自有贡献（仓库所有者创作或已书面取得再许可权）可直接用于商业版本；
  - 第三方历史贡献需贡献者自愿补签（声明中注明覆盖 2026-10-21 前的贡献），未补签部分不进入商业版本；
  - 维护「贡献者签署记录 + 历史贡献覆盖清单」（落地件：[`cla-signing-register.md`](cla-signing-register.md)），每次商业授权交付前核对。
- **不做的事**：不把未签署贡献者的代码强行改 license，不以「整体作品」模糊授权边界，不在未确认来源时把代码放进商业版本。

## 签署与留档

- 个人：PR 评论声明或 `contact@turaidc.com` 邮件，构成电子签名；记录 GitHub 用户名、签署范围（仅新贡献/含历史贡献）、时间与声明原文。
- 组织：授权代表邮件 + 指定贡献者 GitHub 用户名清单，必要时补盖章扫描件。
- 公开贡献者名单只展示 GitHub 用户名，不公开邮箱等个人信息；签署记录保存至贡献授权存续期间。

## 剩余法务确认

1. 签约主体（个人/公司/基金会）必须与商业许可主体一致，否则商业授权链条仍有缺口。
2. 适用法律与争议解决条款需按主体所在地确定（当前为占位）。
3. 中国法下精神权利不可放弃，第 4 条需确认可执行表述。
4. 职务作品与雇主授权：个人 CLA 与组织 CLA 的衔接需复核。
5. 电子签署（PR 评论/邮件）的证据形式、留存期限与个人信息保护要求。
6. 英文版与中文版冲突时的准据版本。
7. 商业许可价格、发票、退款与续费宽限条款（见 `LICENSE-COMMERCIAL.md` 待法务清单）。
