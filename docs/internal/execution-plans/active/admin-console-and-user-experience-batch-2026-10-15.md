# 管理端与用户端体验整改（夜间批次）

## 背景

v0.4.1 之后积累了一批「能跑但不好用」的问题，横跨管理端可点击性、登录首屏、用户端实例控制台加载体验、管理端实例详情的信息架构，以及语言首屏自适应。共同点是**不影响功能正确性，但直接影响运维效率与客户观感**，因此不会被功能测试发现，只能靠人实际点。

本批次刻意允许「宁多勿少」：多一个能点的入口成本极低，少一个入口会让维护人员反复手工搜 ID。

## 各任务范围与验收

### 1. 管理端补齐可点击链接

问题：列表页大量「明明有 ID 却点不动」的位置，例如用户管理 → 工单，工单列表明明带 ID 却无法跳到工单详情。管理员维护时只能靠肉眼搜 ID。

验收：

- 用户管理内的工单列表、实例列表等子表里的 ID 列可点击并正确跳转
- 工单、财务、商品、用户等列表页的主键列均可点击进入详情
- 已有链接保持不变（新增是叠加，不替换既有入口）
- 链接遵循既有路由约定与权限守卫，不绕过统一鉴权

### 2. 管理端登录验证码首屏慢

问题：验证码在页面加载完成后还要再等两三秒才出现，体感像「页面没加载完」，实际是脚本或接口串行。

验收：

- 定位真实延迟来源（脚本下载 / 接口串行 / 组件初始化 / 第三方域），而不是靠加 loading 掩盖
- 验证码与首屏并行发起，不阻塞页面其余部分渲染
- 失败时给出可重试入口，不出现无限空白

### 3. 用户端实例台预加载 + 加载遮罩

问题：NAT、安全组等面板首次进入时内容空白，只有刷新按钮转圈能指示，极易被误解成「没有数据」。

验收：

- 管理端已有的预加载开关扩展到 NAT / 安全组等面板，默认开启（沿用现有开关语义，不新建第二个）
- 各面板首次加载有明确遮罩与骨架，不能出现「空白但无提示」
- 加载失败与「真的为空」两种状态视觉可区分

### 4. 管理端实例详情信息架构重排

问题：主机名、上游名称、上游 ID、价格、续费价等最该置顶的信息散落在二级菜单或页面下方；低价值信息反而占据顶部。代理客户未展示实际折扣价。

验收：

- 顶部信息区按「识别 → 商务」优先级重排：主机名 → 套餐/上游 → 价格与续费价 → 状态
- 代理客户展示实际成交价与原价对照，口径与订单快照一致
- 低优先级信息下沉到次级区域，不与主信息争抢首屏

### 5. 魔方实例一键跳转上游管理

问题：面对魔方财务的实例，管理员无法从本站直达上游侧的服务详情，需要手工拼接 URL。

验收：

- 对魔方实例展示「跳转上游」按钮，目标为 `{上游地址}/servicedetail?id={上游ID}`
- 非魔方实例不展示该入口
- 上游地址取自既有绑定配置，不新增配置项

### 6. 语言首屏自适应与持久化

问题：首次进入未按客户端语言自适应；修改后的语言在部分路径下没有持久化。

验收：

- 首次访问按浏览器语言自动选择（已是目标语言时直接采用）
- 用户手动切换后持久化，刷新与换路径均保持
- 显式选择优先于自动探测，探测只在「无显式选择」时生效

分 app（最终口径）：

- `frontend-admin-v3` 263 处 / 12 文件（`products/edit.vue` 90、`tickets/detail/index.vue` 37、`content/edit.vue` 34）
- `frontend-user-v4-console` 180 处 / 19 文件（`invoice-detail/index.vue` 36、`service-console/.../OverviewTab.vue` 22）
- `frontend-user-v3-www` 39 处 / 4 文件（`layout/WebsiteLayout.vue` 35）

**落地方式：债务棘轮，不清零**。守卫按「app → 文件 → 处数」冻结存量（`TEMPLATE_CHINESE_BASELINE`）：

- 清单外的文件出现中文 → 红（新代码必须走 `$t()`）
- 清单内文件处数**超过**登记值 → 红（存量只减不增，消息带 `89 → 90` 这样的差值）
- 处数变少 → 绿；顺手把基线数字改小，进度就能出现在 diff 里

这样做而不是「一次性清零」或「干脆放行」：482 处逐条清理不是一次能做完的体量，
而把守卫留在错误口径（少扫、漏扫）等于没有守卫。棘轮让「不许再欠」立刻生效，同时把欠账摊开记账。

**守卫自身的验证**（这一步不能省）：基线态绿 → 把某文件基线调低 1 → **红且消息精确**（`pages/products/edit.vue（89 → 90）`）→ 还原后绿。
一个从没红过的守卫等于没有守卫，这是本轮反复踩到的同一个教训。

**后续批次**（未排期）：

1. 单文件超 50 处的先清：`products/edit.vue`（90）、`tickets/detail/index.vue`（37）、`content/edit.vue`（34）、`notifications/index.vue`（29）、`invoice-detail/index.vue`（36）。每清一个就把基线数字改小。
2. 清理时注意：正则 `[^<>{}]` **排除 `{}`**，含插值的节点（如 `{{ page.keyword }}`）不是命中，动它是回归。
3. 目标是基线表整体退化为空数组，届时可把棘轮换回「必须为零」的严格断言。

## 顺带发现：admin smoke.spec.ts 存在既有失败基线（非本次引入）

跑 `frontend-admin-v3` 全量 e2e 时，`smoke.spec.ts` 有一批失败。当时最需要回答的是
「哪些是本次改坏的」——`smoke.spec.ts` 覆盖的页面恰好与本次两个 agent 改过的文件高度重叠。

用静态方法定位，不靠猜：`getByRole` / `getByPlaceholder` / `getByLabel` 定位的是**页面级 UI 元素**，
其文案必然来自 `src`（模板或语言包），不可能来自用例自己 mock 的接口数据。
因此只要文案在整棵 `src` 树里找不到，这条断言**从写下起就不可能通过**。

结果：236 条含中文的 UI 断言中，**13 条文案在 src 中根本不存在**——

| smoke.spec.ts | 断言类型 | 期望文案 |
| --- | --- | --- |
| 3801 | getByPlaceholder | 搜索邮箱/昵称/手机号（实际为「搜索用户ID/邮箱/手机号/昵称/真实姓名/QQ/身份证」） |
| 4555 | getByRole(name) | 新增供应商 |
| 4645 | getByRole(name) | 优惠券管理（路由标题实为「优惠券列表」） |
| 4816 | getByRole(name) | 推广返利 |
| 4900 | getByRole(name) | 会员等级与返利档位（页面标题实为「等级列表」） |
| 4994 | getByPlaceholder | 搜索公告标题 / 摘要 / 正文 / 别名 |
| 5094 | getByPlaceholder | 日志内容关键词 |
| 5290 | getByRole(name) | 通知管理 |
| 5293 / 5295 | getByPlaceholder | 例如 smtp.qq.com |
| 5299 | getByRole(name) | 保存邮件配置 |
| 5350 | getByRole(name) | 验证码邮件 |
| 5748 | getByRole(name) | 实例规格管理 |

`getByText` / `hasText` 不做此判定——它们经常用来校验用例自己 mock 的数据值（如「李四」「黄金会员」），
不在 src 里是正常的。

**交叉验证**：抽两个样本对照 `HEAD`——`会员等级与返利档位` 该字符串**只存在于 spec**，
HEAD 与工作区的源码中都没有；`搜索邮箱/昵称/手机号` 同理，而 HEAD 的 `users/index.vue`
早已是 `$t('users.index.searchPlaceholder')`。两例都证明这些断言在本次改动之前就是红的。

**结论与边界**：`smoke.spec.ts` 的失败基线为既有问题，不是本次引入。
我逐条静态定位了其中 13 条必失败项，其余失败**未逐条对照 HEAD 验证**，
不排除有本次引入的成分——但本次改动的验证覆盖在「三端构建 + 后端全量单测 + 各端 e2e」，
`smoke.spec.ts` 的其余红灯需单独排期排查。

**建议**：这 13 条应先修正为当前真实文案（或改掉定位策略），否则整份 smoke 套件长期处于
「红了也没人看」的状态，真正的新增回归会被淹没。

## 决策日志

- **「宁多勿少」的链接策略**：管理员找一条记录的路径越短越好，多一个入口不会造成困扰，少一个入口会直接变成一次手工搜索。
- **任务 3 沿用既有预加载开关**：管理端已有该开关，另起一个会出现两个语义相同的开关，后台无从判断该开哪个。
- **验证码问题必须定位根因**：用 loading 遮住症状会让首屏更慢，排查接口串行才是正解。
- **语言基建收敛到 `shared/` 而不是三端各改**：三端原本连存储 key 都不一致（「同域部署互相覆盖」是真会发生的事），各端各修一遍会继续漂移。测试护栏也从「各端必须有字面量数组」改成「真源在 shared、各端必须从它导出」，意图不变但不再允许重复声明。
- **测试库用既有容器而不是新建**：`dbverify-mysql57` 已在跑且正是项目基线版本 5.7.44，复用它避免额外镜像与端口占用；测试库 `idc_test` 与容器原有的 `dbverify*` 库完全隔离。
- **测试绝不使用 `.env` 里的远端库**：远端是真实业务库，测试会写入数据。`.env.testing` 指向独立本地库，这是既有设计，不得绕过。
- **i18n 守卫从「永远绿」修成「真能红」**：修好后立刻欠账 171 处（嵌套口径 1005 处）。这是好事——说明此前所有「模板层无硬编码中文」的结论都不成立。守卫必须用一个**必定该失败的输入**验证过它真的会红。
- **官网白屏只靠运行时才能发现**：`.vue` 第 1 行写 `import`（落在 `<template>` 之外）会被 SFC 解析器忽略，`build`、类型检查、`vue-tsc` 全部通过，只有真跑起来才抛 `ReferenceError`。扫描方法已写进 `pitfalls.md` 3.5。
- **e2e 需要显式锁定 locale**：首屏语言自适应生效后，写死中文的断言会随宿主环境语言变红。被测逻辑与语言无关时，应在用例里 `addInitScript` 固定 `turaidc-locale:<app>`，而不是猜当前会渲染成什么语言。
- **代理价优先找同源接口而不是改后端契约**：管理端详情接口缺代理价字段，但续费预览接口的价格由同一个 `AgentDiscountService::apply()` 算出，与订单快照一致。给详情接口擅自加字段会引入第二个真源。
- **既有失败要用静态可判定的方式分离，而不是靠抽样猜**：`smoke.spec.ts` 与本次改动面高度重叠，
  无法靠肉眼判断责任。用「`getByRole`/`getByPlaceholder` 的文案必然来自 src」这一性质做静态筛查，
  一次锁定 13 条从写下就不可能通过的断言，再抽两例对照 `HEAD` 确认，结论才站得住。
- **e2e 语言只在配置层钉一次**：语言自适应生效后，控制台一次跑出 13 failed / 7 passed，全是「宿主语言英文 vs 断言中文」。修法是在各 app 的 `playwright.config.ts` 顶层 `use.locale` 钉 `zh-CN`，覆盖全部 spec；随后控制台 **20 passed / 0 failed**。
  刻意**不**在每个 spec 里写 `addInitScript` 设 localStorage——那是第二套机制，而且走的是「显式选择」分支，与配置层钉的「浏览器探测」分支不同源，留着会让「到底谁决定了语言」变得难以判断。已把三个 spec 里的重复钉法全部移除。
- **过时的 e2e 断言按当前产品行为修正，而不是改产品迁就测试**：`service-console-tabs` 断言面板型控制台只有「总览 / 账单」，而现在的产品行为是「总览 / 产品配置 / 账单」+ 上游自定义区域。逐条核对 `isPanelConsole()` 的判定链（先看 `console_template`、再看 `machine_category.key`）确认代码正确后，改的是断言。该 spec 从 1 passed / 2 failed 变为 **3 passed / 0 failed**。
