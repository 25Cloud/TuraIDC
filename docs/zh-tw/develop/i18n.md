# 國際化（i18n）規範

TuraIDC 三個前端（`frontend-admin-v3` / `frontend-user-v3-www` / `frontend-user-v4-console`）與後端
統一支援 **四種語言**：簡體中文、繁體中文（臺灣）、繁體中文（香港）、English。

前端負責介面文案，後端負責校驗訊息與業務異常訊息，兩側共用同一套 locale 程式碼。本文是唯一規範來源；
改語言、加文案、接入未國際化的介面，都按這裡執行。

自動化測試見 `backend/tests/Unit/I18nLocaleConsistencyTest.php`，它會在構建前攔住絕大多數回退。

## 一、语言集合

| 代码    | 语言             | 说明                                               |
| ------- | ---------------- | -------------------------------------------------- |
| `zh_CN` | 简体中文         | **词条真源**。所有文案先写在这里                   |
| `zh_TW` | 繁體中文（台灣） | 由 `zh_CN` 经 OpenCC `cn→twp` 生成，**不手工维护** |
| `zh_HK` | 繁體中文（香港） | 由 `zh_CN` 经 OpenCC `cn→hkp` 生成，**不手工维护** |
| `en_US` | English          | 人工翻译                                           |

### 繁体必须分台湾与香港

繁体「字」大多相同，差异在「词」，两者不能互相替代：

| 简体 | 台灣 `zh_TW` | 香港 `zh_HK` |
| ---- | ------------ | ------------ |
| 数据 | 資料         | 數據         |
| 网络 | 網路         | 網絡         |
| 软件 | 軟體         | 軟件         |
| 用户 | 使用者       | 用戶         |
| 文件 | 檔案         | 文件         |
| 默认 | 預設         | 默認         |
| 视频 | 影片         | 視頻         |
| 邮箱 | 電子郵件     | 電郵         |

用一份繁体词条覆盖两地，会有一半用词是错的。

代码沿用 TDesign / Element Plus 的原生命名，不自造 `zh-Hans` 之类的变体，
这样组件库语言包可以直接挂载。

**默认语言是 `zh_CN`**，`fallbackLocale` 同为 `zh_CN`：任何语言缺词条时回落到简体中文，
而不是显示空白或裸 key。

### locale 从哪来

```
localStorage 里的 turaidc-locale / tdesign-starter-locale
  → 命中 supportedLocales 则采用
  → 否则 zh_CN
```

管理端、用户控制台沿用 TDesign starter 的 `tdesign-starter-locale`；官网用自己的
`turaidc-locale`。两者互不干扰，因为它们是不同应用。

## 二、詞條檔案與 key 命名

```
frontend-<app>/src/locales/
├── index.ts          # createI18n、supportedLocales、组件库语言映射
├── useLocale.ts      # changeLocale / locale / getComponentsLocale
└── lang/
    ├── zh_CN.json    # 真源
    ├── zh_TW.json    # 生成
    └── en_US.json    # 人工翻译
```

三份檔案按點分路徑巢狀，**key 集合必須完全一致**（測試會校驗）。

key 命名：小駝峰點分，**以功能模組開頭**，模組名從檔案路徑推斷：

| 模組                 | 例子                                                     |
| -------------------- | -------------------------------------------------------- |
| `layout`             | `layout.header.aboutUs`、`layout.nav.productCatalog`     |
| `product`            | `product.detail.basePrice`、`product.specSelection`      |
| `content`            | `content.notice.empty`、`content.help.searchPlaceholder` |
| `seo` / `seoLanding` | `seoLanding.usServer.hero.title`                         |
| `common`             | `common.osPicker.version`                                |

規則：

- 全小寫字母開頭、駝峰；不用中文、不用空格
- 同一語義全站同名（`viewAllProducts` 不要又寫一個 `seeAll`）
- 語義化而非按位置命名（`product.detail.totalFee` 好過 `product.detail.label3`）

## 三、翻譯邊界（最容易出事的一節）

### 必須翻譯

- 模板文本節點：`<div>暂无数据</div>`
- 文案屬性：`title` / `placeholder` / `alt` / `aria-label` / `label` / `description` /
  `content` / `empty-text` / `confirm` / `cancel`
- 腳本里**純粹給人看**的字串：`MessagePlugin.error('保存失败')`、`label: '状态'`

### 絕對不能翻譯

| 型別                 | 真例項子                                      | 原因                                                                                 |
| -------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------ |
| **匹配用關鍵詞常量** | `CPU_KEYWORDS = ['cpu','core','处理器','核']` | 拿去和商品配置項的 `field`/`name` 做字串匹配。翻譯後匹配全部失效，商品規格識別會崩 |
| 協議欄位 / API 引數  | `configoption`、`zapfxxg`、`regdate`          | 對端按字面解析                                                                       |
| 狀態字面量           | `'pending'`、`'active'`                       | 與後端列舉耦合                                                                       |
| 品牌名 / 域名        | `TuraIDC`、`25y.cn`                           |                                                                                      |
| 程式碼識別符號           | 變數名、路由 path、元件名                     |                                                                                      |
| 佔位符               | `{count}`、`{size}`、`%s`                     | 結構不能動                                                                           |

> **這條是血的教訓。** 曾經有指令碼把 `CPU_KEYWORDS` 裡的 `处理器`、`核` 一併替換成 `$t()`，
> 結果官網的 CPU/記憶體分類判斷失效。**凡是不能用眼睛確認「這是給人看的」字串，一律不碰。**

### 判斷方法

問自己一個問題：**這個字串被改動後，系統行為會不會變？**

- 會變（匹配、協議、列舉）→ 不翻譯
- 不會變（純展示）→ 翻譯

## 四、接入方式

### 模板裡用 `$t()`

`createI18n({ globalInjection: true })` 已開啟，模板直接用，**不需要 import**：

```vue
<h1>{{ $t('product.list.breadcrumbRoot') }}</h1>
<input :placeholder="$t('product.detail.systemPlaceholder')" />
```

### 腳本里用 `t()`

```js
import { t } from "@/locales";
MessagePlugin.error(t("common.saveFailed"));
```

### 文本節點含混合內容時

只替換命中片段，保留前後文：

```vue
<!-- 原文：产品中心 · 选择一级分组 -->
<h1>{{ $t('product.list.breadcrumbRoot') }}</h1>

<!-- 原文：共 {{ n }} 条数据 -->
<p>共 {{ $t('common.total') }} {{ n }} {{ $t('common.records') }}</p>
```

### 元件庫語言聯動

- **TDesign**（admin / console）：`tdesignLocaleMap` 掛到詞條的 `componentsLocale`，
  由 `getComponentsLocale()` 取出傳給 `useLocale()`。
- **Element Plus**（官網）：由 `App.vue` 的 `<el-config-provider :locale="elementLocale">` 承載，
  `useLocale()` 的 `getComponentsLocale` 提供該值。**不要**再用 `provideGlobalConfig` 傳 locale，
  它的型別不接受 `Ref`，執行期也不響應。

## 五、新增文案的流程

1. 在**元件裡**寫 `zh_CN` 文案
2. 同步補 `en_US` 詞條（key 與 `zh_CN` 對齊）
3. `zh_TW` 不手寫，跑生成指令碼
4. 跑測試

```bash
# 重新生成三端的 zh_TW（zh_CN 改动后执行）
node backend/scripts/i18n/build-zh-trad.mjs

# 护栏测试
cd backend && php artisan test --filter=I18nLocaleConsistency
```

### 繁體轉換（臺灣 / 香港）

統一用 **OpenCC**，不要手寫簡繁對照表——手寫表覆蓋不全，實測 447 個字會漏，
產出「關於我們」這種簡繁混排。

```js
import OpenCC from "opencc-js";
const twp = OpenCC.Converter({ from: "cn", to: "twp" }); // 台湾
const hkp = OpenCC.Converter({ from: "cn", to: "hkp" }); // 香港
```

兩個轉換器都覆蓋不到的詞，在 `backend/scripts/i18n/build-zh-trad.mjs` 裡補，
且**必須區分替換時機**：

- `HK_PRE_TERMS` —— opencc **之前**替換。適用於「記憶體→記憶體」這類
  opencc 不會做詞彙對映的詞（`hkp` 會把「記憶體」留成「記憶體」）。
- `HK_POST_TERMS` —— opencc **之後**替換。港式字典會把部分字反向還原成簡體
  形態（`户`、`税`、`温`），必須在轉換後再改回來，否則輸出根本不是繁體。

## 六、測試護欄

`backend/tests/Unit/I18nLocaleConsistencyTest.php` 校驗：

1. 四份詞條的 key 集合完全一致
2. `zh_TW` / `zh_HK` 都不含簡體殘留
3. 各端 `supportedLocales` 與實際存在的詞條檔案一致，且覆蓋四種語言
4. 元件庫語言對映覆蓋全部 locale（漏一項，分頁/日期等元件文案就不跟隨切換）
5. 程式碼裡 `$t('key')` / `t('key')` 引用的 key 必須存在於詞條，否則介面直接顯示裸 key
6. 模板層不殘留硬編碼中文

> TDesign 沒有獨立的香港語言包（只有 `zh_TW`），所以 `zh_HK` 的元件語言對映到
> `zh_TW`；Element Plus 自帶 `zh-hk`，直接掛載。

**新增文案時忘了補 `en_US`，或忘了重跑生成指令碼出 `zh_TW`/`zh_HK`，測試會直接失敗。**

## 七、後端業務訊息

### 7.1 語言協商

`SetLocale` 中介軟體（註冊在 api 棧最前）決定當前 locale，優先順序：

1. `X-Locale` 請求頭 —— 前端 i18n 的當前語言，由三端 axios 攔截器帶上，最準確；
2. `Accept-Language` —— 瀏覽器語言偏好（識別 `zh-HK` / `zh-TW` / `en-GB` 等，含 q 值排序）；
3. 預設 `zh_CN`。

前端切換語言後無需重新整理，即刻生效。

### 7.2 訊息表以中文原文為 key

`backend/lang/{locale}/messages.php` 的 key 就是拋異常時寫的中文原文：

```php
// zh_TW/messages.php
'商品分组不存在' => '商品分組不存在',
// en_US/messages.php
'商品分组不存在' => 'The product group does not exist',
```

這樣做的三個好處：

- **零呼叫點改動** —— 600 多處 `throw new BusinessException('中文')` 一行都不用改，
  翻譯只發生在 `BusinessException` 構造時；
- **天然回落** —— 新增業務訊息沒翻譯時，查表 miss 直接返回中文原文，不會出現空訊息；
- **可增量** —— 不必為每種語言同時維護一份完整詞表。

> 查表**必須帶 group 字首**：`Lang::get('messages.' . $message)`。
> Laravel 會把不含點號的 key 當成 group 名（去查 `消息文本`[null]），永遠命中不了。

### 7.3 生成指令碼

```bash
node backend/scripts/i18n/build-biz-messages.mjs
```

掃描 `backend/app` 裡所有 `BusinessException('...')`，重新生成 `zh_CN` / `zh_TW` / `zh_HK`。
`en_US` 是人工翻譯的產物，指令碼不覆蓋它 —— 缺翻譯會在測試裡報出來。

### 7.4 日誌不受語言影響

各呼叫層記錄的是**拋異常之前的中文原文**，排障不受介面語言影響。

## 八、切換器放哪

| 端                 | 位置                              | 原因                                       |
| ------------------ | --------------------------------- | ------------------------------------------ |
| admin / v4-console | 設定面板（`layouts/setting.vue`） | TDesign starter 慣例，與主題、佈局設定同處 |
| 官網               | 頁尾（`WebsiteLayout.vue`）       | 官網無設定面板；頁尾不干擾首屏             |

取自各詞條頂層 `lang` 欄位。

## 九、文件站也走同一套語言集合

`docs/` 文件站不再是單語：簡體中文佔根路徑，`/en/`、`/zh-tw/`、`/zh-hk/` 各是一棵映象子樹，語言程式碼與上文四端保持一致，URL 字首用短寫法（`zh-tw` 而不是 `zh_TW`）。

兩處差異要記住：

- **中文是唯一真源**。英文是人工/AI 翻譯，頁面 front matter 記錄 `source` 與 `sourceHash`，中文改動後允許滯後；兩種繁體由 OpenCC 從中文直接生成，中文一改就必須重跑生成指令碼，否則文件校驗失敗。
- **譯文不動程式碼塊**。程式碼、命令、配置鍵在譯文裡逐字保留，校驗指令碼會比對程式碼塊、標題層級與連結目標，任何一處被翻譯都會報錯。

具體命令、front matter 契約與術語表在倉庫 `docs/internal/i18n/` 下，這裡不重複。
