# 訂單與自動開通

使用者付款到拿到機器之間的鏈路：報價 → 建賬單 → 生成內部訂單 → 支付 → 上游開通 → 服務例項。本文按站長的排障順序組織：先看清各狀態的含義，再記住失敗時錢和人分別停在哪裡。使用者側的交易憑證是**賬單**，訂單是內部開通投影。

## 1. 鏈路與狀態

```text
报价(quote_token，10 分钟有效)
   → 建账单 Invoice（用户侧凭证，due_date = 建单 + 7 天）
   → 生成影子订单 Order（内部开通链路）
   → 支付（网关回调或余额）
   → 上游开通 / 续费
   → 服务实例 Service + 账单 fulfillment_pending 清除
```

**訂單狀態**（`OrderStatus`）：

| 值  | 含義   | 說明                                                             |
| --- | ------ | ---------------------------------------------------------------- |
| `0` | 待付款 | 可取消；續費影子訂單與管理員掛賬訂單不受「超時清單一律關閉」影響 |
| `1` | 已付款 | 已收到錢，尚未開始開通                                           |
| `2` | 開通中 | 已提交上游或等待人工開通；**卡在這個狀態就是錢到了機器沒到**     |
| `3` | 已完成 | 服務已啟用（或商品被判定為無需自動開通）                         |
| `4` | 已取消 | 未付款超時或人工取消                                             |
| `5` | 已退款 | 已走退款流程                                                     |

**訂單型別**（`OrderType`）：`new`（新購）、`renew`（續費）、`upgrade`（附加配置，含流量包與主機升級兩種 `kind`）。

**服務狀態**（`ServiceStatus`）：`0` 開通中、`1` 已開通、`2` 已暫停、`3` 已到期、`4` 已取消。**訂單詳情頁是隻讀的**：只有「檢視賬單」「檢視使用者」「檢視服務」三個跳轉，沒有補單、重試、退款按鈕，推進鏈路要走服務詳情頁與賬單管理頁（見第 5、7 節）。

後臺入口：後臺 → 全部訂單（`/admin/finance/orders`）、普通訂單、續費訂單、附加配置、訂單詳情（`/admin/finance/orders/:id`）。賬單側在後臺 → 賬單管理，可取消未付賬單。

使用者側：官網/使用者入口 → 我的訂單、我的賬單（`/client/orders`、`/client/invoices`）、我的服務（`/client/services`）。

## 2. 下單時服務端校驗什麼

建單入參只有這幾項：`product_id`、`billing_cycle`、`quantity`、`config`、`quote_token`、`user_coupon_id`、冪等鍵。金額不由客戶端決定：服務端按商品價格 + 配置項加價 + 初裝費重算，再套代理折扣與優惠券，最後用 `quote_token` 裡的金額校驗；對不上就報「訂單配置與報價不一致，請重新獲取報價」。

按順序會攔下這些情況：

1. 商品不存在或已下架 →「產品已下架」。
2. 商品庫存不足 → 見[商品與計費](products.md)第 6 節。
3. `purchase_requires` 開啟實名時未實名 →「該商品需要實名認證後才能購買」；開啟手機號時未繫結 →「該商品需要繫結手機號後才能購買」。
4. `quantity` 不為 1 →「當前暫不支援一次購買多個服務例項，請分次下單」。**多開必須分次下單**，同一次請求下多臺機器在這條鏈路上不成立。
5. 報價憑證無效或過期 →「報價憑證已失效，請重新整理配置後重試」（有效期 10 分鐘）；缺少冪等標識 →「請求缺少冪等標識，請重新整理頁面後重試」；計費週期無價格 →「無效的計費週期」。

**防重複建單**有三層：冪等鍵對映（有效期 15 分鐘）、請求指紋（180 秒內同商品同週期同配置同優惠券複用同一張賬單）、以及 `invoices(user_id, idempotency_key)` 唯一索引兜底。使用者連點提交不會生成多張賬單。

## 3. 支付與回撥

支付入口都是未認證路由（網關回調需要）：

- 支付寶：`POST /api/v2/payment/alipay/notify`，獨立驗籤中介軟體 + 限流 60 次/分鐘按 IP。
- 其他閘道器：`GET|POST /api/v2/payment/notify/{gateway}`，簽名校驗中介軟體 + 限流 60 次/分鐘按 IP。

處理順序是「先驗籤 → 再鎖 `payments` 行 → 再冪等判斷（已成功的直接返回成功）→ 事務內更新賬單與訂單投影」。**改回調地址或金鑰後必須重跑一次真實小額支付**，因為驗籤失敗在回撥方看來和超時無法區分，會一直重試。支付渠道配置見[支付渠道配置](../configure/payment.md)。

未支付賬單與訂單在**建單後 5 分鐘**（`paymentSessionTtlSeconds()`）被定時任務關閉，`actor_name` 記為 `schedule:invoice-cleanup`。但賬單自身 `due_date` 是 7 天——**7 天這裡只是催收口徑，不是付款視窗**。

兩類豁免這條 5 分鐘規則，也正因為從未扣過庫存，取消時不會回補庫存：續費賬單（`type = renew`）與其影子續費訂單按 `due_date` 計費，否則續費提醒永遠發不出去；管理員手動開通產生的掛賬賬單與訂單（`config_snapshot.admin_manual = true`）。

## 4. 支付完成後的自動開通

支付成功進入履約時，`new` 與 `renew` 型別**在回撥請求內同步執行**，同步失敗才回退到 `provision` 佇列重試。佇列任務 `ProcessPaidOrderFulfillmentJob` 的引數：最多 3 次嘗試、單次超時 1200 秒、退避 30/120/300 秒、唯一鍵為訂單 ID、`WithoutOverlapping` 防併發。

自動開通用四個條件同時成立才會真正提交上游（`shouldAutoProvision`）：

1. `products.auto_setup = 1`；
2. 商品已繫結供應商（解析出的供應商 ID 大於 0）；
3. 商品已繫結上游商品 ID；
4. 該供應商外掛宣告支援開通能力。

**任何一項不成立，服務會停在「開通中」並寫入原因「待人工開通」，訂單停在「開通中」。** 最常見的一種：商品勾了「自動開通」，但沒有繫結上游商品，使用者付了錢機器不會自己出來。另一種是上游返回了非 `active` 的狀態，訂單同樣停在「開通中」，**沒有自動兜底重試**，只能靠「使用者產品狀態同步」定時任務後續推進或人工處理（未在程式碼中確認該狀態會自動把訂單推進到「已完成」）。

## 5. 開通失敗：現象、重試與人工重跑

**失敗時寫在哪裡**（排障時按這個順序看）：

| 位置                                                | 內容                                                                                 |
| --------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `services.provision_data.provision_error`           | 失敗原因（業務異常取原訊息，其他異常統一為「上游開通失敗，請檢查供應商配置或日誌」） |
| `services.suspended_reason`                         | 同一訊息截斷到 200 字，服務列表裡能直接看到                                          |
| `services.provision_data.last_provision_attempt_at` | 最近一次嘗試時間                                                                     |
| 服務上游繫結表的開通嘗試記錄                        | `success` / `failed` 與失敗原因，含訂單號、上游商品 ID，用於回溯每次提交             |
| 日誌                                                | 關鍵字 `[自动开通] 支付后上游开通失败`，含訂單號、服務 ID、供應商 ID、上游商品 ID    |

失敗後服務狀態回到 `0`（開通中），訂單保持 `2`（開通中）。

**自動重試的邊界**：佇列層 3 次嘗試用盡後，`failed()` 鉤子把已付未履約的新購賬單標記 `requires_refund = true` 並寫 error 日誌。**它只打標記，不自動退款**——程式碼註釋明確要求人工先與上游核實。標記的跳過條件是：訂單型別不是 `new`、賬單不是已支付、訂單已完成。若失敗原因是上游餘額不足，會被識別出來單發通知，但訂單不會暫停，需要人工充值後重跑。

**人工重跑入口有兩個，別用錯**：

| 入口             | 位置                                                                                                                                     | 行為                                                                                      |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 重新提交上游開通 | 後臺 → 使用者管理 → 使用者詳情 → 服務例項管理 → 服務詳情 →「手動開通」按鈕（按鈕僅在服務處於 `0` 開通中**且** `provision_error` 非空時可用） | 調 `retryFailedProvision()`，重走一遍上游購物車：清空購物車 → 加入商品 → 結賬 → 取例項 ID |
| 關聯上游例項     | 同一入口的彈窗（標題「手動開通 / 關聯上游」），填「上游例項 ID」                                                                         | 把已有上游例項繫結到本地服務，不再向上游下單                                              |
| 命令列重跑       | 伺服器執行 `php artisan provision:retry-failed`                                                                                          | 預設 **dry-run**，只掃描並列印；加 `--execute` 才真重試；`--limit=50`、`--max-retries=3`  |

命令列重跑的「孤兒單」判定口徑是三個條件同時成立：服務處於 `0` 開通中、訂單處於 `2` 開通中、`provision_data.provision_error` 非空。達到 `retry_count` 上限（預設 3）的會被跳過並提示需人工介入。它會在失敗時累加 `provision_data.retry_count`、`last_retry_at`、`last_retry_error`。

**動手前必須先核實上游**：上游開通流程是「清空購物車 → 加購 → 結賬 → 取例項 ID」，沒有上游冪等鍵回查。若上一次失敗發生在「結賬已成功、取例項 ID 之前」，直接重跑會**再開出一臺**。所以先登入上游確認是否已存在該例項；已存在就用「關聯上游例項」，不要再點重新提交。這條限制寫在命令原始碼的註釋裡，也是它預設 dry-run 的原因。

**錢已經收了但確實開不出來**：賬單被標記 `requires_refund` 後，人工核實再走退款。退款與庫存回補的關係見[商品與計費](products.md)第 6 節。

**開通失敗的另一個常見原因是上游供應商側的問題**，憑據、連通性與上游商品繫結是否正常，見[上游供應商對接](../configure/upstream.md)。

## 6. 自動續費與到期提醒

**自動續費**（`AutoRenewService`，定時任務「服務自動續費」）在到期前 **3 天**執行（取配置 `idc.auto_renew_days_before`，預設 3），掃描條件同時滿足：`services.auto_renew = 1`、狀態為已開通**或**已到期、`expires_at` 落在目標日當天。

處理邏輯：

1. 先按服務當前計費週期算出應收金額。
2. 若這個到期日已經存在「使用者已支付但未履約完成」的續費訂單，**跳過扣款並等它履約**，避免重複建單。
3. 餘額不足或應收金額不大於 0 → 不扣款、**不寫已執行標記**，下一次排程重試（表現為「餘額補上後自動續費會自己成功」）。
4. 餘額充足 → 建立續費訂單並用餘額支付，然後走與手動續費相同的履約鏈路。
5. 拋異常 → 寫 error 日誌、清除執行標記，等待重試。

同一服務在同一到期日只會被處理一次（執行日誌的唯一規則鍵含到期日與提前天數）。餘額不足、拋異常兩種情況下標記會被清除，所以會反覆重試而不是隻試一次。

**續費金額用的是服務上的鎖定價格，不是商品當前價格**。服務建立時寫入 `locked_pricing`（開通時快照的各週期標準續費價，基準是**未打折原價**），續費時在此之上再疊加代理折扣與優惠券。這樣做是為了避免代理使用者每輪續費被二次疊加折扣。若 `locked_pricing` 為空，會按「續費基準原價 ÷ 當前週期月數」推導各週期價。**所以改商品價格不會立刻影響老服務的續費金額**；要讓老服務按新價續費，需要單獨調整服務的續費價格設定（該操作在後端支援，管理端入口未在程式碼中確認）。

**到期前提醒**在到期前 7 / 3 / 1 天各發一次郵件與站內信（這三個天數是程式碼內固定值 `[7, 3, 1]`，後臺配置裡沒有可改的入口）。**自動生成續費賬單**在到期前 7 天視窗內為開啟自動續費的服務建一張待付賬單，由「賬單自動化維護」定時任務執行。

## 7. 自動掛起與釋放

四個開關都在**後臺 → 自動化策略**（`/admin/automation`）頁，預設值取自 `SettingService::defaultAutomationConfig()`：

| 配置項                          | 預設值 | 作用                                 |
| ------------------------------- | ------ | ------------------------------------ |
| `expire_suspend_enabled`        | 開     | 到期自動暫停總開關                   |
| `expire_suspend_after_days`     | `0`    | 到期後多少天暫停；0 表示從到期次日起 |
| `expire_suspend_notify_enabled` | 開     | 暫停後發通知（郵件 + 站內信）        |
| `expire_terminate_enabled`      | **關** | 暫停後自動釋放總開關                 |
| `expire_terminate_after_days`   | `7`    | 暫停後多少天釋放                     |

**暫停**（`ServiceLifecycleAutomationService::suspendExpiredServices`）的執行條件：`expire_suspend_enabled = 1`、服務狀態為已開通、`expires_at` 早於「當前時間 − `expire_suspend_after_days`」。比較是**嚴格小於**，所以預設值下「到期當天」不會被暫停，從次日第一輪任務開始命中。

暫停時把服務狀態改為已暫停、`suspended_reason` 寫「已到期」、並在 `provision_data.expired_suspended_at` 記下暫停時刻。寫之前會重新讀一次狀態與到期時間，**剛續費成功（狀態或到期時間已變）的服務不會被誤暫停**。

**釋放**（`cancelExpiredServices`）分三步，且預設關閉：

1. 時間預檢：釋放時刻 = **暫停時刻** + `expire_terminate_after_days`（`expire_suspend_after_days` 只在 `expired_suspended_at` 缺失時用於兜底推算）。未到點直接跳過，本輪不改任何狀態。
2. 調上游銷燬例項（對齊魔方下游 `Host::terminate` 協議）。銷燬失敗時**保留暫停狀態、下一輪重試**，本地不做任何變更。
3. 本地置為已取消並清空 `suspended_reason`、移除 `expired_suspended_at`。若在上游銷燬期間服務被續費恢復，本地**跳過取消並寫警告**：`[定时任务] 上游实例已销毁但本地服务状态已被并发变更，请人工核实`——此時上游機器已經沒了，必須人工補償。

**兩個必須注意的判斷點**：

- `expire_terminate_after_days` 的下限是 1（配置層會把它鉗到不小於 1），計時起點是**暫停時刻**而不是到期時刻。所以「到期後 30 天才暫停 + 釋放 7 天」＝第 37 天釋放，而不是第 7 天。
- 若到期已久、遠超 `expire_suspend_after_days`，`expired_suspended_at` 從未被寫過時，兜底值取「`expires_at` + `expire_suspend_after_days`」，可能**已經是過去時間**。這意味著**開啟釋放開關的那一輪，這些老服務會被立刻釋放**。開啟前先核對現有已暫停服務的到期時間。

## 8. 排程依賴與驗證

以上自動化全部由排程心跳驅動，任務名與頻率：

| 任務             | 頻率                            | 做什麼                                                         |
| ---------------- | ------------------------------- | -------------------------------------------------------------- |
| 服務自動續費     | 每 4 個心跳槽（約 15 分鐘一槽） | 餘額自動續費                                                   |
| 服務生命週期維護 | 每 15 分鐘（可配）              | 到期暫停、暫停通知、到期釋放                                   |
| 賬單自動化維護   | 每小時（可配）                  | 續費提醒、自動建續費賬單、賬單到期提醒、逾期標記、續費履約補償 |
| 賬單與充值清理   | 每 15 分鐘（可配）              | 關閉超時未付的賬單、訂單與充值單                               |
| 使用者產品狀態同步 | 每心跳槽                        | 拉上游例項狀態回本地                                           |

心跳槽預設 15 分鐘。心跳或佇列不執行時，第 4、6、7 節裡所有「自動」都不會發生，而使用者看到的現象是「已付款但一直開通中」。部署與排程配置見[部署與排程](../deploy/scheduling.md)。

**聯調與驗證清單**：

1. 用一筆真實小額訂單走通「下單 → 支付 → 自動開通 → 收到訂購提醒」，確認訂單落到「已完成」、服務落到「已開通」。
2. 把商品的 `auto_setup` 開啟但不綁上游商品，付一筆，確認服務停在「開通中」且原因是「待人工開通」——這驗證了人工兜底路徑是否可見。臨時改錯上游憑據再付一筆（記得回滾），確認 `provision_error`、`suspended_reason`、失敗嘗試記錄三處都有內容。
3. 把某個測試服務的 `expires_at` 改到昨天，手工觸發一次「服務生命週期維護」，確認它被暫停且 `suspended_reason` 為「已到期」。
4. 建一張賬單不管它，5 分鐘後確認狀態變已取消，且記錄裡能看到 `schedule:invoice-cleanup`。
