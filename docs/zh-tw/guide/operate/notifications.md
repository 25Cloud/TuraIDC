# 通知與站內信

本文面向帶客服團隊的站長與運營主管，講清站內信、郵件、簡訊三條通知通道各自怎麼開關、模板怎麼配、哪些業務動作會真的發信，以及發不出去時從哪個後臺入口查。變數語法、模板編號與觸發點都取自當前程式碼；某項能力「後端有定義但程式碼裡沒有呼叫」的地方會直接寫明。

## 1. 三條通道的分工與總開關

| 通道   | 儲存與投遞                                              | 總開關位置                                  | 預設值 |
| ------ | ------------------------------------------------------- | ------------------------------------------- | ------ |
| 站內信 | 寫 `user_notifications` 表，使用者在控制台檢視            | 無全域性開關；受使用者自己的通知偏好約束        | 開啟   |
| 郵件   | 走郵件驅動（整合外掛）同步或入隊傳送，落 `message_logs` | 「站點內容 → 站點設定」裡的「啟用郵件通知」 | 關閉   |
| 簡訊   | 走簡訊驅動（整合外掛），落 `message_logs`               | 「站點內容 → 站點設定」裡的「啟用簡訊通知」 | 關閉   |

兩個總開關的儲存名分別是 `notification.email_enabled` 與 `notification.sms_enabled`，取值為 `1`、`true`、`on` 時才算開啟。它們只攔「系統主動發信」，不攔兩條旁路：

- 「整合外掛」頁裡的測試發信走驅動直髮，不受總開關約束——測試成功不代表對外能發。
- 關閉總開關後，系統仍會先寫一條 `pending` 的 `message_logs` 記錄，再以「郵件通知未啟用」或「簡訊通知未啟用」把這條記錄置為 `failed`。所以日誌裡查得到失敗記錄、錯誤資訊就是這句話，這是判斷「是開關沒開而不是通道壞了」的最快依據。

通道的「發不發得出去」還取決於驅動能不能解析出來：郵件與簡訊都先從當前啟用繫結裡挑一個可用驅動，挑不到就報「郵件驅動 [xxx] 未註冊」或「簡訊驅動 [xxx] 未註冊」。也就是說開關開了、模板也配了，但外掛沒裝或沒繫結，一樣發不出去。配置步驟見[郵件與簡訊](../configure/mail-and-sms.md)。

## 2. 站內信

站內信是唯一不依賴外部通道的通知，外掛沒配好也能送達。使用者在控制台的通知中心看到的是**兩類內容的合併流**：一類是公告（內容文章 + 已讀記錄），一類是個人通知（`user_notifications`）。未讀數也按這兩類相加。

每條個人通知包含型別、標題、正文、跳轉連結和一段結構化資料。與工單相關的型別有 4 個：

| 型別常量                  | 觸發時機                                 | 跳轉                   |
| ------------------------- | ---------------------------------------- | ---------------------- |
| `ticket_staff_reply`      | 員工回覆工單，或上游管理員回覆經回撥寫入 | `/client/tickets/{id}` |
| `ticket_pending_reminder` | 員工回覆後長時間無客戶跟進，關閉前催辦   | `/client/tickets/{id}` |
| `ticket_auto_closed`      | 工單被超時自動關閉                       | `/client/tickets/{id}` |
| `ticket_reopened`         | 工單被重開（管理端或客戶自己觸發）       | `/client/tickets/{id}` |

運營要點：

- **寫入是防禦性的。** 表不存在或寫庫拋錯時只記一條 warning 日誌，不會阻斷建單、回覆等主流程。所以「站內信少了」可能是寫入被吞，去 `storage/logs/laravel.log` 搜 `[站内信] 写入失败`。
- **營銷類受使用者偏好控制。** 寫入時帶營銷標記的通知，只在使用者開啟了 `marketing_alert` 時才落庫；工單、賬單這類業務必要提醒不受影響。
- **標題會被截斷**到 191 字元；正文按寫入內容原樣儲存，不截斷。
- 使用者在控制台可以逐條已讀或全部已讀；已讀狀態存 `read_at`，不存在「已讀但未讀數不減」的情況——未讀數就是 `read_at` 為空的行數。

## 3. 郵件模板與變數

模板入口在「站點內容 → 通知與介面 → 郵件模板」，許可權碼 `settings.view`；點進單個模板是「郵件模板詳情」頁，同一個頁面也服務簡訊模板。模板不是純設定項，而是 `notification_templates` 表裡的行，按 `channel`（`email` / `sms`）+ `code`（編號）唯一。

系統內建 31 個郵件模板（編號 `100001` 至 `100031`），全部由 `EmailNotificationTemplateDefaults` 提供預設主題與 HTML 正文，可用命令 `php artisan app:seed-email-templates` 冪等恢復預設。欄位與影響範圍：

| 欄位                   | 說明                                                         |
| ---------------------- | ------------------------------------------------------------ |
| `subject`              | 郵件主題模板；渲染後會去掉換行                               |
| `content`              | 正文模板，可填完整 HTML 文件或正文片段；片段會被套上統一外框 |
| `is_enabled`           | 關掉後該模板的郵件**直接跳過傳送**，不寫日誌、不報錯         |
| `variables`            | 該模板可用變數清單，頁面上以「可用變數」展示                 |
| `provider_template_id` | 僅簡訊：運營商稽核通過的模板 ID                              |

改主題或正文後 `is_custom` 會被標記為自定義；沒有「一鍵回滾單個模板」的按鈕，恢復預設要重跑上一條命令（會覆蓋全部郵件模板的自定義內容，慎用）。

變數佔位符有兩種寫法，郵件與簡訊都支援：

- <code v-pre>{{變數名}}</code> 直接替換。在**郵件正文**裡，HTML 模板中的替換值會被轉義，純文本模板則自動轉成段落。
- <code v-pre>{{#變數名}}…{{/變數名}}</code> 條件塊：變數有值時保留塊內內容，空值（`null`、空字串、`false`）時整塊刪掉。郵件 <code v-pre>{{login_tip}}</code>、簡訊正文裡的可選段落都靠它。

此外簡訊正文額外支援單花括號 `{变量名}`，用於相容運營商自有模板語法；郵件正文不支援單花括號寫法。兩個變數 `site_name` 與 `site_logo` 由系統自動注入，不需要呼叫方傳入。寫成 <code v-pre>{{ }}</code> 之外的其它形式（例如拼錯的變數名）不會被替換，而是原樣留在正文裡，因此**改完模板務必用測試傳送看真實結果**。

預覽與測試：詳情頁右側是即時預覽，右上角「測試傳送」會按模板裡出現的全部變數自動填充示例值（聯絡方式類變數給的是示例值），真實走一次傳送鏈路並回顯成功/失敗條數。測試傳送需要 `settings.manage` 許可權，且一次只允許一個收件人。

## 4. 工單通知的實際觸發點

下表是當前程式碼裡**真實會發**的工單通知。收件人範圍由工單處理人決定，規則見[工單與客服](tickets.md)第 4 節。

| 業務動作                 | 郵件模板                    | 收件人             | 同時寫站內信 |
| ------------------------ | --------------------------- | ------------------ | ------------ |
| 客戶新建工單             | `100026` 管理員新工單提示   | 客服（見下方規則） | 否           |
| 客戶回覆工單             | `100027` 管理員工單回覆通知 | 客服（見下方規則） | 否           |
| 員工回覆工單             | `100024` 工單新回覆通知     | 客戶               | 是           |
| 工單超時自動關閉         | `100025` 工單自動關閉通知   | 客戶               | 是           |
| 工單重開                 | 無郵件                      | —                  | 是           |
| 關閉前催辦               | 無郵件                      | —                  | 是           |
| 上游管理員回覆經回撥寫入 | 無郵件                      | —                  | 是           |

三個容易踩的點：

- **客戶側只有「員工回覆」和「自動關閉」發郵件**，重開與催辦只有站內信。想讓客戶一定看到，就要接受「他必須登入控制台」這個前提。
- **給客服的兩封郵件受處理人影響極大**：工單未指派時發給全部啟用且持 `ticket.reply` 的管理員，已指派時只發給處理人一個人。指派出去了，就等於替其他人靜音了。
- **`100023` 工單開通通知、以及簡訊目錄裡的工單類編號（`100010`、`100012`、`100028`）在當前程式碼裡沒有任何呼叫方。** 它們定義了編號與文案模板，但改它們不會產生任何傳送行為（未在程式碼中確認存在其它呼叫路徑）。

模板變數與實際傳參存在缺口，這是已知現象：`100025` 的預設正文含 <code v-pre>{{ticket_closed_at}}</code> 與 <code v-pre>{{close_reason}}</code>，但自動關閉時只傳了 `display_name`、`ticket_id`、`ticket_subject`、`status`、`tickets_url`、`login_tip`，這兩個變數渲染為空。要客戶看到關閉時間，得自己改模板，改用實際傳入的變數（未在程式碼中確認這兩個變數是否計劃補齊）。

## 5. 簡訊的實際能力

簡訊這條通道要先明確一件事：**當前程式碼裡真正會發出去的只有驗證碼簡訊**（編號 `100001`），它只有一個入口——客戶端獲取手機驗證碼介面 `POST /api/v2/client/auth/phone-code`（未在程式碼中確認存在其它傳送入口），用 `purpose` 區分用途：註冊、登入、重置密碼、換綁/繫結手機號、校驗已繫結手機號，以及未指定時的通用場景。該介面限流為每分鐘 3 次，傳送前另按「渠道 + 手機號 + IP」做一道發碼頻控，超限直接返回錯誤而不發簡訊；「校驗已繫結手機號」這一類還要求目標號碼與當前賬號已繫結號碼一致。電子郵件驗證碼走另一條鏈路（`POST /api/v2/client/auth/email-code`，同樣每分鐘 3 次，郵件模板 `100001`）。簡訊側非阿里雲驅動使用系統內建正文，阿里雲驅動走驅動自帶的模板與服務商模板 ID。

其餘簡訊模板的情況是：

- `notification_templates` 裡存在 `channel=sms` 的編號目錄（`100001` 至 `100033`），後臺「簡訊模板」頁可編輯正文、啟用狀態與「供應商模板 ID」，但除驗證碼外的正文**沒有內建預設值**，需要按服務商要求自行填寫。
- 目錄裡的業務編號（登入提醒、續費提醒、賬單提醒、工單類等）**在當前程式碼中沒有呼叫方**（未在程式碼中確認存在其它呼叫路徑）。配了也不會發，不要據此向客戶承諾簡訊提醒。
- 阿里雲驅動的驗證碼正文由外掛按 `purpose` 提供，系統層只保留等價的回退文案；`purpose` 不影響系統其它邏輯，也不改變日誌裡的模板編號。

投放前的最小驗證：在「整合外掛 → 簡訊」頁確認已啟用並繫結驅動，再用「簡訊模板」頁對 `100001` 做一次測試傳送，然後去「日誌中心 → 日誌管理 → 簡訊日誌」看 `status` 是否為 `success`。

## 6. 使用者的接信偏好

使用者在控制台「通知偏好」裡能改的開關存在使用者表上，介面是 `GET/PUT /api/v2/client/auth/notification-preferences`。它們對系統發信的影響並不相同，混為一談會得出錯誤結論：

| 使用者偏好                | 實際影響                                                             |
| ----------------------- | -------------------------------------------------------------------- |
| `marketing_alert`       | 控制帶營銷標記的站內信是否落庫；**預設關閉**，關閉時營銷通知直接丟棄 |
| `login_email_alert`     | 是否傳送登入提醒郵件；電子郵件為空或該值為 0 時登入提醒被靜默跳過        |
| `login_notify`          | 登入通知的當前生效值，未設定時回退取 `login_email_alert`             |
| `login_location_alert`  | 異地登入提醒                                                         |
| `password_change_alert` | 密碼變更提醒                                                         |
| `phone_change_alert`    | 手機號變更提醒                                                       |
| `email_change_alert`    | 電子郵件變更提醒                                                         |

也就是說：**使用者關不掉工單、賬單這類業務通知**——站內信照寫、郵件照發。能被使用者關掉的是營銷推送與安全提醒，而安全提醒關掉後賬號被盜用也沒有郵件可查，續費與工單通知不受其影響。

## 7. 傳送日誌與排查入口

三條通道的記錄都落在 `message_logs` 表，後臺按通道分兩個頁面展示，許可權碼都是 `log.list`：

| 頁面                               | 列表裡能直接看到的列                                                                 | 常用過濾器                                                            |
| ---------------------------------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| 「日誌中心 → 日誌管理 → 郵件日誌」 | 收件人、模板編號、主題、正文摘要、狀態、驅動、Trace ID、錯誤資訊、記錄時間           | 電子郵件、外掛 ID、驅動、Trace ID、關鍵詞（模板編號/主題/正文）、狀態     |
| 「日誌中心 → 日誌管理 → 簡訊日誌」 | 接收號碼、模板編號、內容摘要、狀態、驅動、Trace ID、服務商請求號、錯誤資訊、記錄時間 | 手機號、外掛 ID、驅動、Trace ID、關鍵詞（模板編號/請求號/內容）、狀態 |

排查按固定順序走，能省掉大部分來回：

1. **先確認動作有沒有觸發**：工單是否被指派決定了收件人範圍；客戶手機號/電子郵件是否為空決定客戶側郵件是否被靜默跳過（服務端在收件人為空時直接返回，不記日誌）。
2. **再看總開關**：日誌裡出現「郵件通知未啟用」「簡訊通知未啟用」就是開關問題，不是通道問題。
3. **再看模板開關**：模板被停用時郵件是**完全跳過**的——不寫日誌、不報錯。日誌裡查不到記錄，又確認動作和開關都正常，就去模板頁核對 `is_enabled`。
4. **再看驅動**：報「驅動未註冊」說明外掛沒裝、沒啟用或沒繫結；報驅動自己的錯誤碼說明是服務商側問題，錯誤原文就在 `error_msg` 欄位裡。
5. **最後看 Trace ID**：日誌裡帶 `trace_id`，同步發給服務商排查時用它對齊同一次請求。

幾個後臺入口能直接串起上下游：郵件與簡訊日誌每行都有「詳情」，正文、請求號與錯誤資訊在那裡看全；詳情裡帶 ID 類欄位時可按 ID 型別（工單 ID、使用者 ID、訂單 ID 等）跳到對應頁面。工單維度的傳送情況可回到工單交流頁對照；工單**上游投遞**另有專門頁面「日誌中心 → 日誌管理 → 上游工單投遞」（過濾器含工單號、回覆 ID、原因碼、供應商），上傳與清理記錄在「上游附件上傳」，自動任務（含工單自動關閉）在「自動任務日誌」。

關於日誌內容本身：郵件正文與簡訊正文在日誌裡是**完整儲存、不脫敏**的，收件地址也按原值展示，這是為了讓運營能真實複核發出去了什麼。相應地，這條資料裡會出現客戶電子郵件、手機號與通知正文，按貴站的許可權管理決定誰能看「日誌中心」——`log.list` 是一個單獨的許可權碼，不要隨手發給所有人。

## 8. 失敗重試與限流

重試能力只覆蓋三個入隊任務，它們的引數完全一致：最多嘗試 3 次，退避間隔 30 秒、120 秒、300 秒，單次超時 120 秒，重試耗盡後由 `failed()` 記一條 warning 日誌並帶上收件地址與上下文。

| 任務                                  | 覆蓋的通知           |
| ------------------------------------- | -------------------- |
| `SendTicketNotificationEmailJob`      | 工單相關的全部郵件   |
| `SendClientLoginEmailAlertJob`        | 使用者登入提醒郵件     |
| `SendClientLoginFailureEmailAlertJob` | 使用者登入失敗提醒郵件 |

其餘郵件與全部簡訊都是**同步傳送、不重試**：`NotificationService::sendEmail` 與 `SmsService::sendTemplateSms` 在請求內直接呼叫驅動，失敗立刻把異常拋回撥用方（同時把 `message_logs` 的狀態更新為 `failed` 並寫入 `error_msg`）。工單郵件也只在佇列可用時才排隊：佇列驅動為 `sync` 時改為「響應後傳送」，`database` 驅動下 `jobs` 表不存在、`redis` 驅動下沒有可用客戶端時同樣退回不重試的路徑。

傳送側沒有額外的通知專用限流；真正攔你的是介面層的限流，例如客戶建單、回覆、關閉各為每分鐘 10 次，圖片上傳每分鐘 12 次。批次觸達要自己控制節奏，撞到限流時才會在日誌裡看到服務商返回的 429 之類的錯誤。

## 9. 上線前的通知體檢

按順序做一遍，能在放量前發現絕大多數通知問題：

1. 「站點設定」裡兩個總開關開啟，站點名稱與 Logo 已換成自家品牌（模板裡的 <code v-pre>{{site_name}}</code>、<code v-pre>{{site_logo}}</code> 取的就是這兩個值）。
2. 「整合外掛」裡郵件與簡訊各自啟用並綁定了一個驅動，用到「測試」頁確認連線正常。
3. 用「測試傳送」各發一次郵件與簡訊驗證碼（兩邊的編號都叫 `100001`，按通道區分），確認收到。
4. 去「郵件日誌」「簡訊日誌」確認兩條記錄都是 `success`，並記下它們的 Trace ID 以熟悉排查入口。
5. 用一個測試賬號走一遍：提交工單、客服回覆、超時催辦（可臨時把自動關閉小時數調小來驗證）、自動關閉。核對四條站內信與兩封客戶郵件是否都到。
6. 確認改過正文的模板仍能渲染：詳情頁預覽沒有殘留的 <code v-pre>{{ }}</code> 佔位符，測試傳送的正文與預期一致。
7. 密碼變更、登入提醒等安全郵件的開關由使用者自己掌握，釋出公告時說明可以在控制台通知偏好裡調整，避免客服被當成開關責任方。
