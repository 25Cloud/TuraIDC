# 使用者與分銷

本文面向運營 TuraIDC 的站長，說明使用者怎麼進來、賬號怎麼保護、實名怎麼審、會員等級與代理折扣怎麼配、返佣怎麼發、提現怎麼批。欄位名與預設值取自後端程式碼，後臺路徑取自管理端路由。

## 1. 註冊與賬號歸屬

- **註冊欄位**：`account`（必填，電子郵件或手機號，識別不出型別時報「請輸入正確的電子郵件或手機號」，最長 100）、`code`（必填，6 位驗證碼）、`password`（必填，至少 8 位，需帶確認欄位）、`nickname`（可選，最長 50）、`email` / `phone`（可選）、`referral_code`（可選，最長 24）。
- **必須驗證碼**：按 `account` 判定走簡訊碼還是電子郵件碼，失敗分別提示「簡訊驗證碼錯誤或已過期」「電子郵件驗證碼錯誤或已過期」。
- **註冊同時建號與推薦碼**：寫入 `users` 記錄（`status` 預設 `1` 正常）與 6 位大寫字母數字的 `referral_code`；餘額賬戶 `user_accounts` 按需建立，各金額預設 `0.00`（後臺建使用者會立即建好賬戶行）。註冊時還會寫入 `last_login_at` 與 `last_login_ip`。
- **推薦關係在註冊環節繫結一次**：與建號在同一個事務裡完成。推薦碼為空、推薦人不存在、推薦人就是自己時靜默放行（不報錯也不繫結）；繫結成功會寫一條 `client.register.referral_bound` 操作日誌。推薦功能總開關關閉時同樣不繫結。
- **後臺建使用者**：入口是使用者列表的「新增使用者」，表單欄位為 電子郵件、暱稱、手機號、密碼；服務層另支援初始 `balance` 與 `credit_limit`（預設 `0`），當前表單沒有暴露這兩項。電子郵件重複報「電子郵件已存在」，手機號有唯一性校驗。

## 2. 登入與安全策略

- **兩種登入方式**：密碼登入與驗證碼登入（電子郵件碼或簡訊碼）。兩種方式下 `users.status !== 1` 都會被拒，報 40300「賬號已被停用」。
- **賬號狀態**只有一個開關：`users.status`，`1` 正常、`0` 停用，在使用者詳情的「編輯」彈窗裡切換。
- **Token 有效期**：預設 `1440` 分鐘（24 小時）過期、`10800` 秒（3 小時）閒置超時，任一到達即失效。管理員給使用者改密會立即吊銷該使用者全部已簽發 token——這是處置盜號的主入口。
- **人機驗證場景開關**：入口在 系統 → 外掛管理 → 人機驗證（`/admin/integration-plugins/captcha`）。可關的是「使用者登入」與「管理員登入」；**強制開啟、不可關閉**的是「使用者註冊」「傳送電子郵件驗證碼」「傳送手機驗證碼」。未儲存過的開關按「預設開啟」處理。
- **應急通道**：`php artisan captcha:scene --list` 檢視各場景狀態，`php artisan captcha:scene admin_login off` 關閉管理員登入的人機驗證，`php artisan captcha:scene --disable-plugin` 整體停用驗證碼外掛（一次顯式的全站決定）。強制場景不接受配置關閉，改庫也無效。
- **失敗次數軟鎖定**（僅在驗證碼外掛**未啟用**時生效，作為兜底）：
  - 賬號加 IP 維度：失敗達到 `5` 次即鎖定，計數視窗 900 秒；
  - 賬號維度：需要 `3` 個以上不同 IP 且賬號失敗達到 `10` 次才鎖定，計數視窗 1800 秒。加這條限制是為了防止第三方從單一 IP 反覆嘗試目標賬號名就能鎖死他人賬號；
  - 登入成功會把上述計數全部清零。
- **軟鎖定不落庫**：它儲存在限流計數里，所以後臺**沒有「解鎖」按鈕**。要麼等視窗過期，要麼讓使用者在驗證碼通道成功登入一次（驗證碼通道與密碼通道的計數互相獨立）。
- **驗證碼觸發閾值**（外掛啟用時）：賬號加 IP 失敗 `1` 次即要求、賬號失敗 `1` 次即要求、單 IP 失敗 `8` 次即要求。管理端與客戶端使用互相隔離的計數作用域，同名管理員與客戶不會互相累加，也不會互相解鎖。

## 3. 實名認證

- **欄位**：`is_verified`、`verification_status`、`verification_message`、`verification_certify_id`、`real_name`、`id_card`、`verified_at`。
- **判定通過**只有一條口徑：`is_verified` 等於 `1`，或 `verification_status` 等於 `2`。
- **狀態取值**：`0` 未認證、`1` 待認證、`2` 已認證、`3` 認證失敗、`4` 待認證、`5` 已駁回。`5` 由管理員在後臺「解綁」產生，落庫時同時寫入駁回原因（預設「管理員駁回」），介面上顯示為「已駁回」，資料效果是解除繫結。
- **管理端入口**：使用者 → 實名列表（`/admin/users/verification`）與實名管理（`/admin/users/verification/manage`），許可權 `verification.list`。駁回/解綁需要額外許可權 `verification.unbind`，駁回原因必填；人工訂正資料走 `PUT /v2/admin/verifications/{user}` 介面。
- **認證外掛**：目錄 `backend/plugins/certification/`，內建 `alipay_certify`（支付寶）、`baidu_face`、`leaf_face`（人臉）、`smapi`、`stay33`、`demo_verification`。啟用與配置入口：系統 → 外掛管理 → 實名認證（`/admin/integration-plugins/verification`）。
- **實名與業務的聯動**：
  1. 商品的 `purchase_requires.require_verification` 開啟後，未實名使用者下單被拒（40301「該商品需要實名認證後才能購買，請先完成實名認證」）；同一組開關裡的 `require_phone` 用於強制繫結手機號（40302）。
  2. 申請提現必須先實名（見第 7 節）。
  3. 充值是否必須實名由設定項 `finance.recharge_requires_verification` 決定，預設開啟，入口在設定頁「賬戶與財務」標籤頁，見[財務與賬單](finance.md)。

## 4. 會員等級與返利比例

會員等級**不影響商品售價**，它只決定推薦人拿多少返佣。

- **表結構** `member_levels`：`name`、`code`、`sales_amount_min`、`sales_amount_max`、`reward_rate`、`status`、`sort_order`、`remark`。
- **管理端入口**：營銷 → 會員等級（`/admin/member-levels`），許可權 `member_level.list` / `member_level.manage`。
- **欄位與限制**：`等级名称`（不能為空、不能重名）、`等级编码`（留空時由名稱生成，同樣不能重複）、`累计销售额下限`（預設 `0`，不能小於 0）、`累计销售额上限`（留空表示不封頂）、`返利比例（%）`（`0`–`100`）、`排序值`、`状态`（預設啟用）。
- **等級歸屬**：按使用者累計銷售額落在哪個**啟用**等級的區間內判定，命中多個時取 `sales_amount_min` 最大的那個。區間不允許重疊，儲存時會校驗並報「等級銷售額區間與現有等級重疊」。
- **銷售額什麼時候漲**：推薦人的下級完成一筆新購時，把訂單實付額累加進推薦人的 `total_sales_amount`，再用**累加後**的金額解析等級並取該等級的 `reward_rate`。升級與返佣在同一筆交易裡一起發生。
- **改動規則的代價**：儲存等級後會派發一個全域性唯一的非同步任務重算存量使用者等級（分批，每批 200 個使用者）。任務冪等，結果只由累計銷售額與當前規則決定，中斷後重跑即可收斂。
- **刪除限制**：等級下仍有使用者時刪除被拒（「當前等級下仍有使用者，無法刪除」）。等級列表快取 5 分鐘，儲存後自動失效。

## 5. 代理分組與折扣矩陣

代理折扣按「代理組 × 商品折扣組」的矩陣配置，是給渠道客戶降價的主要手段。

- **表結構**：
  - `agent_groups`：`name`、`code`、`status`、`default_discount_rate`、`sort_order`、`remark`；使用者通過 `users.agent_group_id` 歸屬某個組。
  - `product_discount_groups`：`name`、`code`、`min_discount_rate`（最低折扣率，下限保護）、`cost_rate`（成本率）、`status`、`sort_order`。
  - `agent_group_discounts`：`agent_group_id`、`product_discount_group_id`、`discount_rate` 三列構成的矩陣。
- **管理端入口**：營銷 → 代理折扣（`/admin/agent-discounts`），三個標籤頁依次是 代理組、商品折扣組、折扣矩陣；許可權 `agent_discount.list` / `agent_discount.manage`。
- **折扣率是百分比，不是折數**：`100` 是原價，`90` 是九折。取值必須在 `0`–`100` 之間，低於商品折扣組的 `min_discount_rate` 會被拒（「折扣率不能低於商品折扣組最低折扣率」）。
- **解析順序**：
  1. 使用者沒有代理組，或代理組 `status` 不是 `1` → 不打折；
  2. 商品掛了商品折扣組、該組 `status` 是 `1`，且矩陣裡存在這個「代理組加商品折扣組」的組合 → 用矩陣裡的 `discount_rate`；
  3. 以上都不成立時回退到代理組的 `default_discount_rate`；這一項為 `null` 表示不啟用回退，仍按原價。
- **成本價保護**：折後金額不能低於成本金額（原價 × 商品折扣組的 `cost_rate`），否則報「代理折後金額不能低於成本價」。注意走第 3 條回退分支時成本率按 `0` 處理，該分支不會觸發成本價校驗。
- **刪除限制**：代理組下還有使用者 → 「當前代理組下仍有使用者，無法刪除」；商品折扣組下還有商品 → 「當前商品折扣組仍有商品，無法刪除」；`code` 重複 → 「編碼已存在」。
- **給使用者指定代理組**：使用者 → 使用者詳情 → 「編輯」彈窗 → `代理组` 下拉（下拉里的 `0` 表示無代理分組，儲存為 `null`），需要 `user.manage` 許可權。

## 6. 折扣疊加規則

這是最容易被問到的口徑，結論是**相乘與相減，不是二選一取最優**。實際計算只發生在下單建賬單時，順序固定：

1. 按商品配置與計費週期算出原價；
2. 套用代理折扣：折後金額 = `round(原价 × 代理折扣率 ÷ 100)`，折扣率取第 5 節解析出的值（沒有代理關係時是 `100`，即不變）；
3. 在**折後金額**上計算優惠券抵扣；
4. 賬單應付額 `amount` = `max(折后金额 − 券抵扣, 0)`，`discount` 記錄券抵扣額。

因此三者同時存在時的公式是：**應付 = 原價 × 代理折扣率 ÷ 100 − 優惠券抵扣**。會員等級的 `reward_rate` 不參與這條計算，隻影響推薦人的返佣比例。

改價的視窗在下單前：報價憑證 `quote_token` 繫結折後金額與券後應付額，有效期 600 秒；提交時服務端重新校驗，客戶端改不動價格。

## 7. 返佣、凍結與提現審批

**返佣怎麼算**：

- 前提是返利總開關 `referral.enabled` 為開（預設開啟）、訂單型別是新購、訂單狀態屬於 已付款 / 開通中 / 已完成、買家有推薦人。
- 計算基數是訂單實付額（`paid_amount`，為空時取 `amount`），不是商品原價。
- 比例取推薦人按**累加後**累計銷售額命中的等級 `reward_rate`；沒有命中任何等級時用全域性配置 `referral.reward_rate`（設定頁預設 `10`，範圍 0–100）。
- 獎勵先落到 `user_accounts.referral_frozen_balance`，並寫一條 `referral_rewards`（`status` 為 `0` 凍結中），`available_at` 由 `referral.reward_freeze_days` 決定（設定頁預設 `4` 天）。
- 到期由 `php artisan referral:release-rewards` 把凍結轉為可提現（`status` 變 `1` 已釋放），使用者申請提現時也會先觸發一次釋放。
- 沒有訂單的賬單走另一條發放路徑，只認型別為 `new` 或 `normal` 且狀態為已付的賬單。
- 退款會把獎勵反向衝減（`status` 變 `2` 已回退），分別從凍結餘額或可提現餘額扣回；若獎勵已釋放而可提現餘額不足，系統記 warning 而不是靜默吞掉。
- 管理端入口：營銷 → 推廣概覽（`/admin/referral`）與獎勵記錄（`/admin/referral/rewards`），許可權 `referral.list`。
- **繫結不可更改**：推薦關係在註冊時繫結一次，已有推薦人時再傳推薦碼不會覆蓋。推薦人與被推薦人最近登入 IP 相同時繫結被拒，並寫 `referral.bind.blocked_same_ip` 操作日誌。

**提現怎麼批**：

- 使用者申請入口是控制台 `/client/referral`，欄位 `amount`、`method`、`remark`；`method` 只有 `alipay`（支付寶，也是預設值）與 `balance`（提到站內餘額）兩個值。
- 提交門檻按順序校驗：必須已實名 → 金額大於 `0` → 不低於 `referral.withdraw_min_amount`（設定頁預設 `20`，提示「獎勵滿 X 元才可提現」）→ 可提現餘額足夠 → 不能已有一筆待處理申請（「已有待處理提現申請，請等待稽核完成」）。選支付寶時還必須已繫結支付寶，否則「請先繫結支付寶」。
- 申請時錢就動過了：可提現餘額減少、提現中餘額等額增加，並寫一條 `withdraw_apply` 流水；提現單狀態為 `0` 待處理。
- 審批入口：營銷 → 提現稽核（`/admin/referral/withdrawals`），許可權 `referral_withdrawal.list`。只有待處理的單據帶「通過」與「拒絕」兩個按鈕，彈窗裡通過備註可留空、拒絕原因必填。
  - **通過**：提現中餘額轉為已提取餘額，狀態變 `1` 已通過。若方式是 `balance`，同一事務裡還會把等額金額加到 `cash_balance`，並寫一條 `account_type` 為 `cash`、`event_type` 為 `referral_withdraw_approved` 的現金流水。
  - **拒絕**：金額退回可提現餘額，狀態變 `2` 已拒絕。
- **打款確認**：後端提供 `POST /v2/admin/referral-withdrawals/{withdrawal}/payment-confirmations`，只接受已通過（狀態 `1`）且方式不是 `balance` 的單據，必須填寫打款單號，成功後狀態推進為 `3` 已打款並回填打款時間。**管理端當前只有通過/拒絕兩個按鈕，未在程式碼中確認存在打款確認入口**，需要時請按介面直接呼叫並留痕。
- 使用者側四個獎勵餘額的含義：`referral_frozen_balance` 凍結中、`referral_available_balance` 可提現、`referral_pending_withdrawal_balance` 提現中、`referral_withdrawn_balance` 已提取。使用者詳情的「推薦資訊」標籤頁展示推薦碼、當前等級、直接推薦人數、累計獎勵與可提現額。

## 8. 管理端使用者操作與邊界

- **使用者列表**（`/admin/users`，許可權 `user.list`）：列為 ID、賬號、暱稱、餘額、已開通服務數、代理組、狀態、註冊時間；篩選支援關鍵詞與狀態。
- **使用者詳情**（`/admin/users/:id`，許可權 `user.detail`）標籤頁：基本資訊、推薦資訊、產品/服務、賬單、資金流水、工單、操作日誌、通知記錄。頂部餘額卡片旁的按鈕直接開啟「資金管理」彈窗，規則與風險見[財務與賬單](finance.md)。
- **可編輯欄位**：`nickname`、`status`（正常/停用）、`phone`、`password`（留空不改，至少 8 位）、`agent_group_id`（需 `user.manage`）。手機號回顯為脫敏值時按「未修改」處理，不會被寫壞。
- **代理登入**：使用者詳情頁可對目標使用者發起「登入為使用者」，被停用（`status` 不等於 `1`）的賬號會被拒（「該客戶賬號已被停用，無法代理登入」）。這是一次顯式的代操作，請只在自己確知需要時使用。
- **不能做什麼**：
  - 不物理刪除使用者：使用者模型使用軟刪除，刪除動作不會讓歷史賬單、流水與獎勵記錄消失。
  - 不直接改資料庫裡的使用者狀態或餘額欄位：前者繞過實名與風控鏈條，後者繞過樂觀鎖與流水寫入。
  - 不把「駁回」當成日常的解除實名叫法：駁回等於解綁，會同時寫入駁回原因，且只有當前已認證的使用者才能操作。
  - 不改推薦關係：註冊後繫結即固定，未在程式碼中確認存在後臺改綁入口。
  - 不手工給獎勵餘額加數：獎勵餘額只能由返佣與提現兩條鏈路變動；需要補差請走現金餘額調整並寫明原因。
