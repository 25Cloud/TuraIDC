# 工單與客服

本文面向帶客服團隊的站長與運營主管，講清工單從提交到關閉的完整流轉、權限與可見範圍、自動預回覆與超時關閉的行為邊界，以及工單傳遞到上游供應商後的收發現狀。文中字段名、狀態值與菜單路徑均取自當前代碼；管理端頁面為 `frontend-admin-v3`，「後台入口」指該端的實際路由。

## 1. 部門、分類與狀態

工單部門固定四類，取值 `sales`、`support`、`billing`、`abuse`，頁面標籤依次為「銷售」「技術支持」「財務」「投訴」。部門只是分類標籤，不決定由誰處理——處理人靠指派。

優先級取值為 `1` 至 `4`，標籤為「低」「中」「高」「緊急」；客戶建單時未提交優先級則落庫為 `2`（中）。工單傳遞到上游時優先級會被映射成 `low` / `medium` / `high` 三檔：`4` 映射 `high`，`3` 與 `2` 都映射 `medium`，`1` 映射 `low`。

狀態是會話推進的唯一依據，取值如下。

| 值  | 標籤     | 由什麼動作變成這個狀態                 |
| --- | -------- | -------------------------------------- |
| 0   | 開啟     | 客戶建單成功                           |
| 1   | 客戶回覆 | 客戶追加回復                           |
| 2   | 員工回覆 | 管理員回覆；預回覆命中時建單即為該狀態 |
| 3   | 已關閉   | 管理員關閉、客戶關閉或超時自動關閉     |

關閉原因存 `close_reason`，標籤由系統給出：`admin` 管理員關閉、`client` 用戶關閉、`auto` 自動關閉。重開成功會把它清空。

## 2. 權限與可見範圍

工單相關的權限碼共 5 個，全部必須顯式授予；除下面標明隱含的部分外，`ticket.manage` 不隱含傳遞與預回覆權限。

| 權限碼                    | 能做什麼                                              | 後台入口                             |
| ------------------------- | ----------------------------------------------------- | ------------------------------------ |
| `ticket.list`             | 看工單列表、工單詳情、回覆列表、上游投遞狀態與日誌    | 工單處理 → 工單管理 → 工單列表       |
| `ticket.reply`            | 以員工身份回覆工單、上傳圖片、撤回自己 2 分鐘內的消息 | 工單交流頁內操作                     |
| `ticket.manage`           | 關閉、重開、指派處理人、重新註冊上游回調              | 工單交流頁內操作                     |
| `ticket.delivery_manage`  | 工單傳遞規則、上游部門列表、上傳防護配置              | 工單處理 → 工單管理 → 工單傳遞設置   |
| `ticket.pre_reply_manage` | 工單預回覆設置                                        | 工單處理 → 工單管理 → 工單預回覆設置 |

`ticket.manage` 隱含 `ticket.list` 與 `ticket.reply`；系統內置默認角色拿不到 `ticket.list` 之外的任何工單權限，「訪客」類角色只有 `ticket.list`。

可見範圍的邊界要記牢三點：

- 列表接口沒有按部門或處理人過濾的能力，拿到 `ticket.list` 的人看到的是全部工單。要限制某人只看自己負責的工單，只能靠不給他 `ticket.list`。
- 客戶電郵在後續 API 響應裡按權限碼 `privacy.view_raw` 脫敏成 `首字母***@域名`；缺少該權限的賬號看到的是掩碼，無法據此聯繫客戶。工單通知郵件本身不受影響，仍發往真實地址。
- 「指派處理人」下拉只列**啟用**（`status=1`）且持 `ticket.reply` 的管理員，一次最多返回 100 人；停用或沒有回覆權限的賬號既不能出現在候選裡，也不能被指派（接口會直接報「該管理員無工單處理權限」）。

## 3. 建單、回覆與撤回

客戶建單要求標題非空（最長 200 字），內容與圖片至少有一項（內容最長 10000 字）；圖片單條消息最多 9 張，上傳接口只接受 `image/jpeg`、`image/png`、`image/webp`，單張不超過 5 MB，落盤在 `storage/app/private/tickets/`，只能通過簽名短鏈讀取。工單可以關聯一個屬於該客戶自己的服務實例，選了別的用戶的服務會被拒絕。

管理端不提供「代客戶建單」入口：工單隻能由客戶在會員中心提交。管理員在客戶視角看到的建單能力只在服務控制台的報障入口（服務實例 → 提交工單），最終仍以該客戶身份建單。

員工回覆、客戶回覆共用同一條消息通道：正文可為空但必須有圖片，正文按純文本清洗入庫。兩條約定容易被忽略：

- **沒有內部備註。** 系統裡不存在「僅內部可見」的回覆類型，員工發出的每一條回覆客戶都能在會員中心看到，並會觸發客戶郵件與站內信。要寫內部溝通記錄，不要用工單回覆。
- **撤回有時限。** 只有發送者本人能撤回自己的消息，且距發送不超過 120 秒；撤回後正文清空、附件清空，只保留一條「消息已撤回」佔位。客戶或員工都無法撤回對方的消息。

客戶回覆會把狀態置為「客戶回覆」；員工回覆與上游回調會把狀態置為「員工回覆」。已關閉工單拒絕任何一側繼續回覆，客戶必須先重開。關閉與回覆併發時以行鎖內的先到者為準，後到的一方會收到「工單已關閉」。

## 4. 分配與轉派

指派入口在工單交流頁右欄的「處理人」下拉，保存後寫 `assignee_id`，接口是 `PUT /api/v2/admin/tickets/{ticket}/assignment`，需要 `ticket.manage`。轉派就是再指派一次：重新提交另一個管理員 ID 即可，不需要先解除。

指派會影響通知收件人範圍，這是最容易出錯的聯動：

- 工單**沒有**處理人時，客戶建單與客戶回覆的提醒郵件會發給**全部**啟用且持 `ticket.reply`、且填了電郵的管理員（按電郵去重，只發一次）。
- 工單**有**處理人、且該處理人本身在可接收名單裡時，提醒只發給這一個人，其餘客服收不到。所以指派既是分工，也是「靜音開關」。

工單列表默認篩選是「進行中」（狀態 0、1、2），支持按狀態、優先級、部門、關鍵詞（標題模糊或工單 ID 精確）過濾，每頁默認 20 條、上限 100 條。

### 4.1 工單交流頁與接口限流

工單交流頁（`/admin/ticket-conversations/{id}`）左右分欄：左欄是「溝通記錄」與回覆輸入框，右欄是「提交用戶、工單分類、優先級、處理人、關聯服務、創建時間、關閉原因」的描述列表與處理人選擇器；未關閉的工單才顯示指派區。列表頁點擊標題行即跳進本頁，工單 ID 與客戶 ID 也支持從其他模塊（如日誌中心）跳轉過來。

管理端接口的限流寫在路由上，做批量操作前先知道這些數字，免得撞上「請求過於頻繁」：

| 動作                          | 接口                                                                                                  | 限流                            |
| ----------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------- |
| 管理端回覆                    | `POST /api/v2/admin/tickets/{ticket}/replies`                                                         | 未單獨限流（需 `ticket.reply`） |
| 撤回消息                      | `POST /api/v2/admin/tickets/{ticket}/replies/{replyId}/recalls`                                       | 未單獨限流                      |
| 重開工單                      | `POST /api/v2/admin/tickets/{ticket}/reopen`                                                          | 每 10 分鐘 10 次                |
| 客戶建單 / 回覆 / 上傳 / 關閉 | `/api/v2/client/tickets`、`/tickets/{id}/replies`、`/tickets/upload-images`、`/tickets/{id}/closures` | 每分鐘 10 / 10 / 12 / 10 次     |

## 5. 預回覆（自動首響）

預回覆讓客戶建單成功的瞬間就收到一條員工回覆，避免「提交後無人應答」。配置在「工單處理 → 工單管理 → 工單預回覆設置」，權限碼 `ticket.pre_reply_manage`，對應接口 `GET/POST /api/v2/admin/ticket-pre-reply-settings`，保存動作會寫管理員操作日誌（動作 `ticket.pre_reply.update`）。

| 字段               | 含義                                     | 約束與默認值                                                   |
| ------------------ | ---------------------------------------- | -------------------------------------------------------------- |
| `enabled`          | 是否啟用預回覆                           | 必填；默認關閉，`config/ticket_pre_reply.php` 回退值為 `false` |
| `admin_user_id`    | 以誰的名義發這條回覆                     | 啟用時必填，必須是啟用且持 `ticket.reply` 的管理員             |
| `content`          | 普通工單的預回覆正文                     | 啟用時清洗後不能為空，最長 5000 字                             |
| `upstream_content` | 命中傳遞規則、會推送到上游的工單專用正文 | 可選；留空時回退用 `content`，最長 5000 字                     |

行為邊界必須提前跟團隊對齊：

- 預回覆與建單在同一個事務裡提交，**只對新建工單生效一次**，不是每次客戶回覆都觸發。
- 它會立刻把工單狀態改成「員工回覆」（狀態 2），也就是説自動關閉的倒計時從建單那一刻就開始走了（見下一節）。
- 它**不轉發上游**：投遞日誌裡會留一條 `pre_reply_skipped` 記錄。若工單命中傳遞規則，上游收到的是客戶的首條內容，而不是預回覆。
- 它**不觸發通知**（客戶不會因此收到一封「工單有新回覆」的郵件）。
- 命不命中傳遞規則決定用哪份正文：`upstream_content` 留空時無需判斷，一律用 `content`。
- 配置殘缺時保持靜默：未啟用、沒選管理員、內容清洗後為空、管理員被停用或失去 `ticket.reply`，都不會生成預回覆，也不會報錯——只會在保存時由校驗攔住前三種情況。

## 6. 超時自動關閉與催辦

自動關閉由「自動化策略」頁控制，入口是「系統設置 → 自動化策略」（直連 `/admin/automation`），權限 `schedule.view`，參數存 `automation` 配置組。

| 字段                              | 含義                   | 默認值     | 取值範圍/説明                  |
| --------------------------------- | ---------------------- | ---------- | ------------------------------ |
| `ticket_auto_close_enabled`       | 是否啟用自動關閉       | 開啟       | 關閉後工單隻能人工關閉         |
| `ticket_auto_close_after_hours`   | 員工回覆後多少小時關閉 | `48`       | 1 至 720；代碼內下限強制為 1   |
| `ticket_auto_close_schedule_mode` | 任務執行週期           | 每小時     | 與「執行時間」一起決定運行時刻 |
| `ticket_auto_close_schedule_time` | 任務執行時間           | `00:00:00` | 非每小時週期時用於對齊         |

判定口徑只有一句話：**掃描狀態為「員工回覆」（2）、且 `updated_at` 早於 `now() - 小时数` 的工單**。由此推出四條實際後果：

- 「開啟」和「客戶回覆」的工單永遠不會被自動關閉，哪怕放了半年。
- 客戶每次回覆都會刷新 `updated_at`，倒計時重置；員工回覆同理。
- 關閉時附件只做軟刪標記，文件不刪；重開後歷史附件重新可見。
- 關閉成功後才會發通知：郵件模板 `100025`（工單自動關閉通知）+ 站內信 `ticket_auto_closed`。若工單已被別人搶先關掉，不會重複發信。

催辦在關閉窗口過半時發一次，只發站內信、不發郵件：閾值取 `ticket_auto_close_after_hours` 的一半（向下取整，至少 1 小時），且尚未到關閉閾值。同一輪等待只提醒一次（冪等鍵為 `idle_since:` + 該輪起點時間戳），客戶一旦回覆、時間戳變化，下一輪重新計算。站內信類型 `ticket_pending_reminder`，標題「工單待您處理」。

任務本身註冊在 `ticket-auto-close`（分類「工單管理」），執行記錄在「日誌中心 → 日誌管理 → 自動任務日誌」，也可在站內 `storage/logs/laravel.log` 搜 `[定时任务] 工单自动关闭` 核對關閉了哪些工單。

## 7. 上游工單傳遞與回調

傳遞的開關分三層，缺一層就整單不轉發：一是關聯服務所用產品必須綁定**啟用**的 ZJMF 財務接口供應商；二是「工單傳遞設置」裡必須有一條**啟用**的規則命中該工單的部門與產品範圍；三是標題與首條回覆都不能命中該規則的屏蔽關鍵詞。任一層不滿足，工單仍在本站正常流轉，只是不會出現在上游。

規則字段（接口 `GET/POST/PUT/DELETE /api/v2/admin/ticket-delivery-rules`，權限 `ticket.delivery_manage`）：

| 字段                     | 説明                                                        |
| ------------------------ | ----------------------------------------------------------- |
| `name`                   | 規則名稱，最長 120 字                                       |
| `department`             | 命中哪個工單部門，四選一                                    |
| `supplier_id`            | 上游供應商，必須啟用且配好啟用的 ZJMF 財務接口綁定          |
| `provider_key`           | 前端不填，接口固定寫成 ZJMF 財務接口                        |
| `product_scope_mode`     | `all` 全部產品 / `selected` 指定產品                        |
| `product_ids`            | `selected` 時至少一個，且每個產品都要有啟用的 ZJMF 上游綁定 |
| `upstream_department_id` | 上游部門 ID，從上游拉取後選擇，最長 64 字符                 |
| `enabled`                | 是否啟用該規則                                              |
| `sync_admin_replies`     | 是否把**管理員**回覆同步給上游；關閉則只轉發客戶消息        |
| `mask_keywords`          | 每行一個關鍵詞，命中標題或首條回覆即不轉發，最長 10000 字   |

同一供應商 + 部門 + 產品範圍模式只能有一條規則，重複創建會被拒絕。

轉發與回調的實際行為：

- 工單投遞成功後，**後續歷史回覆會補投**：該工單首條之後的所有回覆會按發送者分別排隊補發，上游不會丟中間的消息。
- 客戶回覆與管理員回覆都會帶前綴標識（`[下游用户消息]` / `[下游管理员消息]`），上游可據此區分來源。
- 上游管理員回覆經回調寫入本站後會顯示為 `upstream_admin` 類型的員工消息，消息上的顯示名取上游傳入的 `admin_name`，缺省顯示「上游客服」。這類回調只寫本地、不再回推上游，避免形成迴環。
- 回調按事件 ID 冪等：同一個事件重複到達只記一條回覆，投遞日誌裡留 `duplicate_event`。回調附件限制為最多 9 張、單張不超過 5 MB、僅 `image/jpeg`、`image/png`、`image/webp`。
- 回調簽名校驗失敗、上游供應商被停用、找不到對應本地工單，都會寫一條 `failed` 投遞日誌並在響應裡給出原因；密鑰讀到空值直接拒絕服務，不會降級放行。

排查入口都在工單交流頁右欄的「上游傳遞」卡片：狀態標籤有「未配置 / 等待發送 / 發送中 / 已轉發 / 轉發失敗 / 未轉發」，另可看上游工單號、嘗試次數、最近嘗試時間、最近結果與投遞日誌分頁。不轉發時會給出原因碼，常見的有 `rule_not_matched`（沒有匹配的啟用規則）、`mask_keyword_matched`（命中屏蔽關鍵詞）、`upstream_product_missing`（服務未配上游產品）、`supplier_binding_disabled`（供應商接口綁定未啟用）。若上游回調地址失效（換域名、改端口），用卡片上的「重新註冊回調」按鈕重發註冊（接口 `POST /api/v2/admin/tickets/{ticket}/upstream-delivery/callback-registration`，需要 `ticket.manage`）。

## 8. 狀態機：每一步能做什麼

| 當前狀態   | 客戶可做                       | 員工可做                                             |
| ---------- | ------------------------------ | ---------------------------------------------------- |
| 0 開啟     | 回覆、關閉、上傳圖片           | 回覆、指派、關閉、重開（重開會失敗，僅已關閉可重開） |
| 1 客戶回覆 | 繼續回覆、關閉、上傳圖片       | 回覆、指派、關閉                                     |
| 2 員工回覆 | 回覆（轉為 1）、關閉、上傳圖片 | 回覆、指派、關閉                                     |
| 3 已關閉   | 重開                           | 重開                                                 |

已關閉狀態下，客戶與員工的回覆接口都會被拒絕，頁面上也不提供回覆框；「重開」是唯一齣口，重開後狀態回到「開啟」、關閉原因清空、關閉期間軟刪的附件恢復可見，同時給客戶寫一條站內信 `ticket_reopened`。管理端重開有每 10 分鐘 10 次的接口限流，客戶側重開同樣受限。

## 9. 出問題先看這裡

1. **客戶説沒收到郵件**：先確認建單/回覆是否真的觸發了通知（工單是否已有處理人，決定了收件人是全體客服還是單人），再去「日誌中心 → 日誌管理 → 郵件日誌」按收件人與模板號查發送狀態，見[通知與站內信](notifications.md)。
2. **客服説看不到某個工單**：工單列表不按人過濾，看不到就是缺 `ticket.list`，去「系統設置 → 權限管理」核對該角色權限。
3. **指派下拉是空的**：説明系統裡沒有啟用且持 `ticket.reply` 的管理員。下拉本身不依賴電郵，但收件人缺電郵時通知會靜默失敗——被指派人也收不到提醒。
4. **工單沒推送到上游**：看「上游傳遞」卡片的最近結果與原因碼，對照第 7 節的三種前置條件；上傳類問題另查「工單傳遞設置」裡的上傳防護開關。
5. **工單被自動關掉了**：核對「自動化策略」裡的自動關閉開關與小時數；判定只看狀態 2 與 `updated_at`，與客戶是否已讀無關。
