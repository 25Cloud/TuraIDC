# 自助退款

插件目錄為 `backend/plugins/addons/auto_refund/`，後台能力域為 `addons`，標識為 `auto_refund`。它把「用戶想退掉某台機器」從工單搬到控制台：用戶自己選機器、填原因、提交；插件按**該商品**配置的退款策略算出可退性並分流到對應通道，最後在台賬裡留痕，由管理員核對上游後結算到用戶餘額。

行為口徑對齊智簡魔方財務的 AutoRefund 插件（v1.3.0）：四種退款類型、三種退款規則、三種退款要求，全部**按商品**配置。真實退多少錢仍以上游與實際結算為準，本站展示的金額是預估。

## 1. 四個概念

| 概念     | 取值                                            | 説明                                                                   |
| -------- | ----------------------------------------------- | ---------------------------------------------------------------------- |
| 退款類型 | 人工審核 / 自動退款 / API 工單退款 / 插件間對接 | 決定提交後走哪條路：只落台賬、立即退款、向上遊開工單、調上游 `api.php` |
| 退款規則 | 按時長 / 按月 / 全額                            | 決定預估金額怎麼算（公式見第 6 節）                                    |
| 退款要求 | 產品首次 / 同類產品首次 / 指定時間內            | 決定「誰還能申請」：同商品首次、同一級商品分組首次、開通後 N 小時內    |
| 時間窗口 | 小時                                            | 只有「指定時間內」這一要求會用到，`0` 表示不限                         |

同一商品同時只能有一種類型、一種規則、一種要求——這與上游一致，不要指望「既按時長又按月」。

## 2. 安裝與啟用

1. 部署後端並跑一次 `php artisan migrate`。建表與登記都由**核心遷移**完成（插件不能自註冊遷移）：
   - `2026_11_01_000001_create_auto_refund_applications_table`：申請台賬；
   - `2026_11_01_000002_register_auto_refund_plugin`：登記插件，**只登記、默認不啟用**；
   - `2026_11_03_000001_create_auto_refund_product_rules_table`：商品退款策略；
   - `2026_11_03_000002_add_channel_and_ticket_to_auto_refund_applications`：台賬補通道與工單字段。
2. 管理端「插件管理」→ 自助退款 → 填配置（第 3 節）→ 啟用。
3. 管理端「財務管理 → 自助退款 → 退款商品策略」給商品逐條配策略（第 4 節）。**沒配策略的商品不會出現在用戶的可申請列表裡**。
4. 重新構建並部署兩個前端（`frontend-user-v4-console`、`frontend-admin-v3`）。

插件停用後兩端入口自動收起（`OptionalFeature::map()` 的 `auto_refund`），接口隨之消失；已產生的台賬與策略保留。

## 3. 配置項

**上游接口通道（退款類型 = 插件間對接時才必須）**

| 配置               | 默認                    | 説明                                                                   |
| ------------------ | ----------------------- | ---------------------------------------------------------------------- |
| 啟用自助退款       | 開                      | 關閉後控制台顯示未開放                                                 |
| 上游接口地址       | 上游 `api.php` 完整地址 | 必須是 POST 端點；只在「插件間對接」類型下使用，留空則該通道判定未就緒 |
| 上游 API KEY       | 空                      | 上游發放的完整密鑰；頁面上的掩碼值無效；加密保存、不回顯               |
| 請求超時（秒）     | 15                      | 超時按「結果未知」處理並佔住該機器的提交閘門                           |
| 提交前校驗上游主機 | 開                      | 提交前先 `query` 確認機器在上游可見                                    |
| 控制台説明文案     | 空                      | 展示在退款中心頂部                                                     |
| 結算備註模板       | 自助退款申請結算        | 寫進退款單的備註前綴，後端會附申請編號                                 |

**上游工單通道（退款類型 = API 工單退款時才必須）**

| 配置            | 默認               | 説明                                                                                                                             |
| --------------- | ------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| 上游工單協議    | `zjfm`             | `zjfm`：智簡魔方財務原生（`/v1/login_api` 換 JWT → `/submitticket`）；`tura`：上游也是 TuraIDC，走既有 `/ticket/create` 投遞鏈路 |
| 上游站點地址    | 空                 | `zjfm` 協議必填                                                                                                                  |
| 上游賬號        | 空                 | `zjfm` 協議的登錄賬號                                                                                                            |
| 上游 API KEY    | 空                 | `zjfm` 協議登錄用的密鑰，加密保存                                                                                                |
| 上游工單部門 ID | 2                  | 上游「財務/退款」部門的 `dptid`，填錯就是把工單發錯部門                                                                          |
| 工單標題模板    | 申請退款           | 支持 `{product_name}` `{host_id}` `{amount}` `{reason}`                                                                          |
| 工單內容模板    | 申請產品無理由退款 | 同上                                                                                                                             |

`zjfm` 協議的成功判據是上游返回 **302 且 Location 含 `supporttickets`**（上游原生接口就是這個行為），也兼容返回 JSON `code=200` 的變體；兩種都不滿足時會在台賬裡留下失敗原因與響應前 300 字。

## 4. 給商品配策略

管理端「財務管理 → 自助退款 → 退款商品策略」：

- 列表能看到**所有商品**，包括還沒配的（狀態顯示「未配置」）。篩選可按關鍵字與配置狀態。
- 逐條編輯：退款類型、退款規則、退款要求、時間窗口（小時）、啟用開關。
- `window_hours` 只有選中「指定時間內」才可填；填 `0` 等同不限。
- 關掉啟用開關 = 該商品不參與自助退款，用戶側看不到。

選擇建議：

| 場景                                     | 類型         | 説明                                                   |
| ---------------------------------------- | ------------ | ------------------------------------------------------ |
| 想讓客服逐單看                           | 人工審核     | 只落台賬，不外發任何請求                               |
| 小額、規則簡單、信任公式                 | 自動退款     | 提交即退款到餘額，無需人工                             |
| 上游是智簡魔方財務，要留溝通記錄         | API 工單退款 | 建本站工單 + 向上遊提工單，上游回覆進工單線程          |
| 上游已裝 AutoRefund 並對本站發了 API KEY | 插件間對接   | 直接調 `api.php` 的 `submit`，用戶可在待審核時自己取消 |

## 5. 用戶與管理端流程

用戶側（控制台「交易記錄 → 退款中心」）：

1. 候選列表只列**本站已開通、且該商品配了策略**的機器；每行標註該機器自己的「類型 · 規則 · 要求」，例如「插件間對接 · 按時長折算 · 產品首次」。
2. 不可申請的行會寫明原因（該商品未開放、未支付、已過期、已續費、升降級過、免費訂單、狀態不支持、已有在途申請、超出時間窗口、上游不可用等）。
3. 提交後按類型給不同話術：自動退款＝已退款到餘額；人工審核＝等待管理員審核；API 工單＝已向上遊提交工單；插件間對接＝已提交上游審核。
4. 只有「插件間對接 + 待上游審核」的申請能自己取消；其它類型沒有可撤銷的上游記錄，頁面不會給取消按鈕。

管理端（「財務管理 → 自助退款 → 退款申請」）：

| 操作         | 作用                           | 注意                                                                     |
| ------------ | ------------------------------ | ------------------------------------------------------------------------ |
| 結算         | 按填寫金額退款到用戶餘額       | 走既有退款鏈路，超出賬單剩餘可退額會被賬務層拒掉；先到上游核對是否已到賬 |
| 駁回         | 標記駁回，不入賬               | 上游拒絕後在這裡收口                                                     |
| 作廢         | 強制關閉卡死/結果未知的申請    | 唯一手動出口，不可撤回，不退款                                           |
| 測試上游連接 | 調 `query` 回報機器數與時間差  | 排查密鑰、地址、出網、時鐘偏差                                           |
| 上游機器對賬 | 列出上游全部機器與本地綁定情況 | 找「上游有本地沒綁」與「本地綁了上游沒了」                               |

詳情抽屜裡能看到退款類型、通道、本站工單、上游工單號與**提交時的策略快照**——策略是可改的配置，沒有快照就沒人能解釋「當時為什麼這台能退、金額怎麼算的」。

## 6. 金額與校驗口徑

預估金額按上游公式：

```text
周期秒数 = 到期时间 - 开通时间
每秒单价 = 首购账单实付 / 周期秒数

按时长：实付 - 每秒单价 * 已用秒数
按月：  实付 - 每秒单价 * 2592000 * ceil(已用秒数 / 2592000)
全额：  实付
结果四舍五入到分；小于等于 0 直接拒绝申请。
```

- 機器處於「未開通完成」狀態時強制按全額算，不看商品配置的規則。
- 三個基數取自本站：**開通時間 = 服務創建時間**、**到期時間 = 服務到期時間**、**首購實付 = 開通那一單的賬單實付額**（不是最近一次續費賬單）。
- 預估只用於展示與工單模板佔位；插件間對接通道**不把金額傳給上游**（上游契約不允許指定金額），實退以管理員結算為準，且受既有可退上限保護。

提交前的硬性校驗（任一命中即拒絕）：商品沒配策略、首購賬單未支付、已有在途申請、已過期、服務已刪除、服務狀態不支持、已續費、首付為 0、升降級過。

## 7. 排錯

| 現象                             | 排查                                                                                  |
| -------------------------------- | ------------------------------------------------------------------------------------- |
| 用戶看不到某台機器               | 該商品有沒有配策略並啟用；機器是否綁定了上游實例（工單/接口通道需要）                 |
| 提交提示「該商品未開放自助退款」 | 策略行缺失或 `enabled=0`                                                              |
| 提交提示「未配置上游工單部門」   | `zjfm` 協議的部門 ID 為空；`tura` 協議既沒配部門也沒有匹配的工單投遞規則              |
| 工單通道報 302 但判定失敗        | Location 不含 `supporttickets`，通常是賬號無工單權限或部門 ID 不存在                  |
| 插件間對接報 401 / 403           | API KEY 無效 / 上游插件授權過期                                                       |
| 申請卡在「結果未知」             | 上游超時或返回非 JSON。先到上游核實是否已建單，再結算或作廢；期間用戶重提會被閘門擋住 |
| 結算報「超過原單可退金額」       | 賬單剩餘可退額不足，按可退額調整                                                      |
| 用戶説上游退了但餘額沒變         | 上游退款 ≠ 本站結算：台賬裡點「結算」才會入用戶餘額                                   |
